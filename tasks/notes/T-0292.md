## What has to be held (found in the code)

A finished run goes up by **two separate streams**, so both need the mark:

| Stream | Plugin | Site | Public surfaces it feeds |
|---|---|---|---|
| Timed runs (`.foseg`, every finished timed segment) | `RunUploadModule` outbox `uploads/pending/` -> `POST /api/runs` | `runs` table | spot boards (`/api/spots/<id>`, `board.txt` = other runners' comparisons in game), the spots list's best + runner count, `/api/runs/<id>` (ids are **sequential**: guessable), `/compare`, the rank / *Spot record* / *Next best* in **other runners'** PB posts (`Runs.Standing`), and **the PB post itself** (`PbFound` -> `PbPosts.Post`) |
| Run mode attempts (codes + log) | `RunUploadModule.Attempts` (`POST /api/attempts`, checkpoints, log) | `attempts` table | *Official runs* (`Attempts.Official`), the attempt page `/attempt/<id>` (ids are 16 random hex: unlisted, not guessable) |

The anti-splice proof needs the site's arrival times (docs/run-mode.md
*Codes and receipts*), so **holding never stops an upload**: checkpoints
and logs go up in real time as now and are judged on arrival; only what
the site *shows* and *posts* changes.

A held run also has to stay out of everything computed for someone else,
or it leaks: another runner's PB post saying "#2 of 5 runners" or "Spot
record: 59.000" with only 4 runners on the board gives the surprise away.
Rule for the build: **a held run counts in nothing served to anyone but its
runner** (boards, ranks, counts, records, the 0.8x "under review" best,
official lists, `/api/runs/<id>` -> 404 as for a hidden run).

## The options

### 1. Per run, per runner, or both

- **A. A runner's setting (the switch).** While it is on, every run and
  attempt the runner uploads is held. Simple, one place, set *before* the
  run - which matters: uploads are automatic and the PB post fires on
  arrival, so a per-run choice made after the run is too late for Discord.
- **B. Per run only** (a "Hold back" button on each finished run). Too
  late for the webhook unless uploads wait for a click - which breaks the
  real-time checkpoints for attempts and the "automatic" rule (decisions.md
  *Run uploads*). Not workable alone.
- **C. Both:** the switch, plus a per-run *Show* in the list to release
  one run and keep the rest held. More UI; useful only if a runner wants to
  show some held runs and not others.

**Recommended: A**, with "release" = release all (see 3). C later if a
runner asks for it.

### 2. Where the switch lives

There is no runner login on the site (the upload token lives in the game),
so **the switch and the release are in game**; the site shows the state.

- **In game, recommended:** the Runs tab's *Upload to the website* section
  (ui-redesign; on main: the upload block of the Runs tab), right under
  *Upload finished runs to forest.deter.cloud*. That section is closed by
  default on the redesign, so its **header summary** says the state while
  folded (UiKit.Section's summary, as *Checkpoint states* shows on / off).
  The run mode line at the top of the Runs tab says it too while run mode
  is on, since that is where a runner looks before a run.
- **Alternatives:** Settings -> Site fold (harder to find; ux check 5 wants
  one place, and the upload toggle is already in the Runs tab); a HUD flag
  (see Q4 - it would be in the video).
- **Site:** no switch. A *Held back* badge on the attempt page (reached by
  the runner's *Copy link*), and a tag on held rows in /admin.

### 3. What "release" does

- **How:** turning the switch off releases everything held, behind a
  two-click confirm like *End run mode* ("Click again ..."), because an
  accidental click would spoil the surprise (ux check 15). One control, one
  meaning: on = held, off = shown.
  Alternative: the switch only governs new runs, and a separate *Show held
  runs* button releases (two controls; a held run can outlive the switch).
- **Order:** the plugin sends the release only once both outboxes hold no
  held file still to send (a run queued offline while held must not arrive
  after the release and stay held forever). Until then the line says it is
  waiting.
- **Dates:** a released run keeps **its own date** (when it was run) in
  every list - the boards and Official runs sort by time; *Recent runs*
  sorts by date and would put it in its true place. The attempt page adds
  one line: "Held back by the runner until <date>." (proposed) - a fact a
  moderator may want, and the receipts' arrival times stay as recorded.
- **Discord on release:** recommended **one post per spot whose released
  best beats the runner's best already shown there** (the same `NewPb`
  rule, against public runs only), with the rank / records worked out at
  release time, and the run's date in the description. Released runs that
  are not a PB post nothing. Caps: the existing ones (official 30 an hour;
  runners' spots 30 an hour, 5 a runner an hour) - a release over many
  spots could hit the per-runner cap; propose posting the official spots
  first, then runners' spots up to the cap, and dropping the rest (logged).
  Alternatives: post nothing on release (the surprise is the runner's to
  announce), or post every held PB in order (noisy).
- **Turning hold back on** never hides runs already shown (that would be a
  delete by another name; deleting stays owner-only - run-mode.md).

### 4. Who still sees a held run

| Who | Sees |
|---|---|
| The runner, in game | their own times as now (local files), the attempts list with *Copy link* (a held row says so), the count of held runs |
| Anyone with an attempt's link | the attempt page with the *Held back* badge - verdict, codes, log as usual (the runner can send it to a moderator) |
| Admins (/admin) | held runs and attempts with a *held back* tag (the flagged list, Activity) - they verify runs, and admins already see hidden ones (Q3) |
| Everyone else | nothing: not in Official runs, boards, counts, comparisons, `/api/runs/<id>`, `/compare`, ranks in others' posts, Discord |

This bends one decision: "**Reports are public** (runners check their own
before submitting; anyone can double-check)" (run-mode.md). A held
attempt's report stays readable by link, and becomes listed on release -
needs the author's OK (Q5).

## Recommended design (A, one switch, release all, post on release)

- Plugin: `Site/HoldBack` (bool, default off). On = the next runs and
  attempts are held. The upload section's header reads *held back* in the
  orange used for "changes something" while on; the run mode state line
  adds it. Off = two-click confirm, then the release once the queue is
  clear; the line says how many runs went public.
- Mark per upload, stamped when the run finishes (so the offline queue
  keeps it): `.foseg` bundles get a header line `hold = yes`
  (`SegmentBundle`; older parsers skip unknown header keys, checked in
  `SegmentBundle.Parse`); attempts send `"hold": true` on
  `POST /api/attempts` and `?hold=1` on the log POST (an attempt started
  offline has only the log); **not** in the hash-chained log, so the chain
  format does not change.
- Site: `held` (0/1) + `released_ms` on `runs` and `attempts`; every query
  that serves others adds `held = 0`; `POST /api/held/release` (Bearer)
  releases the runner's rows, posts the PBs (3), bumps the Official cache
  stamp; `GET /api/held` (Bearer) -> `{ runs, attempts }` for the game's
  count (asked when the tab opens, as T-0144 asks about sent attempts).
