### What was proved live (v0.24.292, Slot 1 at (428, 78, -4))

How: real OS input from a Python `SendInput` script (relative mouse
moves, wheel ticks, a W key by scan code) sent to the focused game
window, sampled over the bridge (`call static:UnityEngine.Input
GetAxisRaw "Mouse X"` and the rest, one call a frame).
`Application.targetFrameRate` was set to 30 for the sampling so each
frame got a few moves, then put back to -1.

1. **`UnityEngine.Input.GetAxisRaw("Mouse X" / "Mouse Y")` works in this
   game.** The InputManager asset (`globalgamemanagers`) has Unity's
   default axes: Horizontal, Vertical, Fire1-3, Jump, `Mouse X`,
   `Mouse Y`, `Mouse ScrollWheel`. While the mouse moved it returned
   0.6 / 0.8 a frame for X. For Y it returned -0.3 / -0.4: a move down
   is negative.
2. **It is the same signal the game's look gets.** Rewired runs with
   `ReInput.configuration.windowsStandalonePrimaryInputSource =
   DirectInput`. In that mode its mouse comes from Unity's Input:
   - `ReInput.controllers.Mouse.GetAxisRaw(0)` read 6 / 8, Unity's value x 10.
   - The Rewired action `Input.player.GetAxis("Mouse X")`, which is what
     `TheForest.Utils.Input.GetAxis` returns, read 0.6 / 0.8, the same as
     Unity.
   - Mouse Y matched as well (-0.3 / -0.4).

   The player's yaw turned about 69 degrees per 1000 counts in every
   run (500 counts: 50.78 -> 85.35; 2000: 85.35 -> 223.64).
3. **With the overlay window open** (`Menu` state, cursor visible and
   unlocked), all three sources still return the motion. The Menu map
   maps the mouse axes too, because VirtualCursor moves with them. The
   yaw did not move (306.62 before and after). So the axes are not
   gated by game state, and the module must gate on `Cursor.visible`
   itself (the author's "nothing while the cursor shows").
4. **The bridge's injected `axis "Mouse X" 1` reaches only
   `TheForest.Utils.Input.GetAxis`.** That read returned 1 and the yaw
   turned 306.62 -> 354.57. The direct Rewired read and the Unity read
   both returned 0. So an e2e test cannot drive the mouse box with
   `axis`. It can with an OS-level `SendInput` (as above), but only
   while the game window has focus.
5. **Keys and the wheel.**
   - A `SendInput` W (scan code 0x11) held for 2 s gave
     `Input.GetKey("w")` True, `anyKey` True and the game's `Vertical`
     1. The bridge picks the string overload, so `GetKey W` throws
     "Input Key named: W is unknown". The plugin uses the `KeyCode`
     overload.
   - A wheel tick (`MOUSEEVENTF_WHEEL` 120) gave `Input.mouseScrollDelta`
     (0, 1) and `GetAxisRaw("Mouse ScrollWheel")` 0.1 on its frame.
6. Nothing in the plugin patches `UnityEngine.Input`: `InputInject`
   patches only `TheForest.Utils.Input`, and `TasInput` binds Rewired's
   `Player`. So Unity reads can never add names to a TAS recording.

**Decision for the build:** read the mouse with
`UnityEngine.Input.GetAxisRaw("Mouse X")` / `("Mouse Y")`. Do not use
Rewired.
- No game name is involved, so there is **no `src/Game/` file**.
- The value is Unity's pointer delta x 0.1 (the asset's default
  sensitivity). It is a sum per frame, so the trail stays the same
  whatever the frame rate. It is unaffected by the in-game sensitivity
  and invert settings: it shows the hand, not the camera.
- The game's camera ignores the mouse while movement is locked
  (cutscenes, `SimpleMouseRotator.GetInput`). The trail still moves
  then, which is fine for "what the runner's hand did".
- Rewired would add a reflection bind and a game name for the same
  numbers, and would mix in a gamepad's right stick under the same
  action.

**Analogue keyboards** (the author asked what is possible): Unity 5.6's
`Input.GetKey` and Rewired's keyboard (fed from Unity in DirectInput
mode) are on / off only. A hall-effect keyboard's travel needs its
vendor SDK, a native DLL such as the Wooting Analog SDK, outside Unity.
A keyboard in "gamepad" mode shows up as a Rewired joystick. Neither is
built. The tiles light on press, with no partial fill.

### Build plan (forest-dev)

On main: the HUD redesign is merged, so `HudWidgets`,

1. **`src/Data/InputLayout.cs`** (pure) + `tests/.../InputLayoutTests.cs`.
   - A list of tiles. Each tile has kind `Key` | `Mouse` (the mouse
     box), a `KeyCode` int, a label, x / y as screen fractions 0..1, a
     size in px at UI scale 1, w / h for the mouse box, and shown.
   - Each tile is placed on its own, with no panel and no grid (author:
     "any key alone or a few spaced anyhow").
   - `Parse(string)` / `Serialise()` use one line, e.g.
     `W 0.10,0.80 48; A 0.07,0.85 48 hidden; Mouse0 0.20,0.80 48; mouse 0.25,0.78 120x120`.
     Parsing is forgiving like `HudLayout`: an unknown key or a bad
     number skips that tile, values are clamped to the screen and the
     sizes to 16..400.
   - `Default()` gives W A S D, Space, LeftShift, LeftControl, Mouse0,
     Mouse1 and the mouse box, near the lower left.
   - Labels: `Shift`, `Ctrl`, `Space`, `M1`..`M5`, letters as-is; any
     other `KeyCode` uses its enum name.
   - Tests cover round-trip, defaults, clamping, junk tokens, duplicate
     keys (keep the first), an empty string (meaning defaults) and
     removing every tile ("none", which stays none).
2. **`src/Modules/InputOverlayModule.cs`**, registered **last** in
   `BuildModules` (after `DeveloperModule`; bridge indexes stay).
   - **Config**:
     - `[Inputs] Enabled` (default off)
     - `[Inputs] Layout` (string)
     - `[Inputs] TrailSensitivity` (float, default 1, the mouse box
       scale)

     All three are registered with `HudWidgets.RegisterProfileEntry`,
     so they switch with the HUD profile (as `PracticeRunModule.Splits`
     does with `_panelX` etc.). Check that a profile written before
     T-0302 loads unchanged.
   - **Off** means `Tick` returns at once: no `GetKey`, no drawing, no
     allocation.
   - **Tick (Update) sampling**:
     - Use preallocated arrays indexed by tile. Per frame: one
       `Input.GetKey(KeyCode)` per key tile (the KeyCode overload,
       never the string one), plus `GetAxisRaw("Mouse X")` and
       `("Mouse Y")` (cached `const string`s) when a shown mouse box
       exists.
     - Keep the press start time for the animation. A press shorter
       than ~50 ms is latched lit for 50 ms, so a one-frame tap shows on
       a repaint.
     - While `Cursor.visible` and not in Edit HUD, nothing lights: the
       sampled values count as up and the trail does not grow (finding
       3).
     - Do **not** read `TheForest.Utils.Input` or Rewired at all (task
       `keep`, finding 6).
   - **Mouse box trail**:
     - A preallocated ring of ~150 points, as in the reference
       (length 150, fade 600 ms).
     - Each frame: pos += (dx, -dy) * TrailSensitivity * k, with the
       position wrapping at the box edges (the reference's *wrap* mode)
       and a timestamp stored per point.
     - Draw on Repaint only, in one `GL.Begin(GL.LINES)` pass with the
       `Hidden/Internal-Colored` material, as `MapModule.DrawOverlay`
       does, with alpha by age.
     - Do not draw a segment across a wrap jump.
     - Pick `k` on the hand deploy so an ordinary flick crosses about
       half the box. With the test's numbers, 0.6 a frame at 30 fps for
       a slow pan, so start at k = 4 px per unit.
   - **Drawing (`DrawScreen` / OnGUI)**:
     - Draw on `EventType.Repaint` only.
     - Each tile is a `UiKit` rounded box in the active `UiPalette`:
       idle uses the card fill + hairline, pressed uses the accent fill

     - Press animation as in the reference: the scale eases 1.0 -> 1.1

       `GUI.matrix` (no font rebuild).
     - Cache the `GUIContent` labels and build them only when the
       layout changes.
     - Use one font size per tile size, taken from the size buckets

       armed, skipping Escape (cancel) and the overlay's own F-keys
       from `HotkeyMap`.
     - Each tile is dragged on screen by itself, and its corner
       resizes it.
     - "Reset to defaults".
     - Every change writes `[Inputs] Layout`.
   - **Log lines** (one per runner action):
     - `Inputs: on` / `Inputs: off`
     - `Inputs: added <key>`, `Inputs: removed <key>`,

## 1. What the reference does

girlglock/input-overlay is an OBS browser source plus a small desktop
server (`input-overlay-ws`, Rust/Tauri) that reads raw input
(Windows RawInputBuffer, Linux evdev) and streams it over a websocket.

- **Keys as tiles.** A layout is a list of tiles, each
  `[key(|key2...), label, w, h, x, y]` in key units (1 unit = 50 px, 8 px
  gap). Default layout: `1 2 3 4`, `TAB Q W E R`, `SHIFT A S D F`,
  `CTRL ALT SPACE`, and on the right a mouse block: `M1`, a scroll tile
  (`- / up / down`), `M2`, under them a **mouse pad**. A tile can bind
  several keys (`key_w|key_up`), take an invisible spacer, or a custom
  label (text or an image).
- **Pressed look.** Each tile has an idle and a pressed colour (fill,
  outline, text), a pressed scale (1.10x), a pressed outline width, a
  glow, a corner radius and an animation time (300 ms). Analogue
  (hall-effect) keyboards fill the tile by how far the key is down.
- **Mouse pad.** A box that draws the mouse's movement as a fading
  trail (fade 600 ms, length 150 points, sensitivity %), mode *wrap* (the
  trail wraps at the box's edges) or *pan* (the view follows the trail);
  optional M1 highlight on the trail; optional travelled distance in cm
  from the mouse DPI (resettable after a fade).
- **Extras.** Gamepad sticks, scroll counters, a key whitelist, a
  separate input-history gimmick (the last presses as a fading list),
  ~40 fonts, colours by picker. Everything lives in the overlay URL
  (compressed JSON), so a layout is shared as a link.
- **Configurator.** A web page: drag tiles on a grid, resize them,
  per-tile label / keys, then copy the URL into OBS.

What carries over: tiles at grid positions, a pressed / idle look, a
mouse block with movement, the layout as shareable data. What does not:
the websocket / OBS part (we draw in the game), analogue keys, gamepads
(the plugin is keyboard + mouse; Rewired does gamepads - a later idea),
fonts by the dozen.

## 2. What a ForestOverlay version would show

A proposed first layout (every word below is **proposed**, not chosen):

```
        [ W ]                 [M1][M2]
   [ A ][ S ][ D ]            [ mouse ]
 [Shift][  Space  ][Ctrl]     [  pad  ]
```

- **Keys:** W A S D, Space, Left Shift, Left Ctrl - the movement keys
  of the game's default bindings (game-notes *The default bindings*:
  "Esc, W A S D, Space, Left Shift, Left Ctrl, ..." are the keys its
  keyboard maps use). Which action each key is (Shift = sprint, Ctrl =
  crouch) is **not** in game-notes - only `Crouch` as a Rewired action
  name is (game-notes *Crouch*). The tile shows the key's own name, so
  the design needs no action name.
- **More keys a runner may add** (from the same bound-key list): E
  (take / use), G, B, Z (rest), C, Q, R, Tab, 1-4. Any Unity `KeyCode`
  can be a tile.
- **Mouse buttons:** M1, M2 (the game's mouse maps use left and right;
  the side buttons are unbound - game-notes), M3-M5 addable (M4 / M5 are
  Paint's default keys, `PaintModule`).
- **Scroll:** a tile lit for a few frames on wheel up / down.
- **Mouse movement:** the mouse pad (a fading trail), or a lighter
  option: a dot / arrow showing this frame's look direction and size.
  See *Reading* for where the numbers come from.
- **Not shown:** Esc and the overlay's F-keys (they are not gameplay).

## 3. How it fits the redesign's HUD

The redesign's rules decide most of this (decisions.md *Overlays are set
up where they are shown*, *HUD profiles*; docs/ui-redesign.md on
`ui-redesign` *HUD customiser*):

- **It is an on-screen panel, like the splits and results panels**: it
  is switched on, set up, moved and sized in **Edit HUD**, in its
  *Panels* group (`ModuleHost.DrawHudEditors` -> the module's
  `OverlayModule.DrawHudEditor` override, as `PracticeRunModule` does),
  never drawn inside a tab. No tab gets an Inputs section.
- **Saved in the HUD profile**: its settings are config entries
  registered with `HudWidgets.RegisterProfileEntry` (as
  `PracticeRunModule.Splits` registers `_panelX` / `_panelY` /
  `_panelWidth`), so they land as `@Inputs.* = ...` lines in
  `config/ForestOverlay/hud/<name>.txt` and switch with the profile. The
  tile layout is one string entry, e.g.
  `@Inputs.Layout = W 1,0; A 0,1; S 1,1; D 2,1; LeftShift 0,2 w=1.5; Space 1.5,2 w=2.5; LeftControl 4,2 w=1.5; Mouse0 6,0; Mouse1 7,0; pad 6,1 w=2 h=2`
  (format proposed), parsed by a pure `Data/InputLayout` (tested,
  forgiving like `HudLayout`: unknown keys skipped, numbers clamped, one
  line). Not a `HudLayout` line: `HudLayout` only keeps `HudLines` keys
  and drops the rest on its next write.
- **Two levels of "where each sits"**, to keep it simple (author's
  *easy to learn, little at once*):
  1. the panel as a whole: dragged anywhere, its corner resizes it (one
     scale, 0.5 - 6x like a placed value), drops on T-0020's snap points
     once that is built;
  2. inside the panel, in Edit HUD only: a tile is dragged to another
     grid cell (quarter-unit steps), its row in the editor has a show
     toggle and a label field; "+ Key" adds a tile by pressing the key
     (as Settings binds a hotkey today), right-click removes it.
- **Look**: tiles are `UiKit` rounded boxes in the active theme
  (`Data/UiPalette`): idle = card colour + hairline, pressed = the accent
  (`#E5C501`) fill, text dark - "colour only means something" (ux.md D18:
  the accent is the active colour). No glow, no scale animation in the
  first version (each is a per-frame cost and a setting); a short
  hold-lit time instead (below).
- **Shown when**: the HUD shows - it follows the HUD's own show / hide,
  as the splits panel does (which cases that covers: read
  `PracticeRunModule.Splits` when building, not assumed here).

## 4. How inputs are read

Two sources exist; the design picks **physical keys** for keys and
buttons, and needs one bridge check for mouse movement.

**A. Physical keys - `UnityEngine.Input.GetKey(KeyCode)`.** Already
proved in this game: the overlay's F-keys (`Core/HotkeyMap`: "Plain
Input.GetKeyDown still sees raw keys") and Paint's Mouse 4 / 5 hold
(`PaintModule`: `Input.GetKey(b.Key)` with `KeyCode.Mouse3` / `Mouse4`,
painted with by the author, v0.24.278). No game name is involved, so it
lives in `src/Modules/` (or `src/Core/`), nothing in `src/Game/`. It
shows what the runner's fingers did, as the reference does, whatever the
game's bindings. Scroll: `Input.mouseScrollDelta` (Unity, no game name).

**B. The game's actions - Rewired.** `Game/WorldEvents` reads every
Rewired action by id (`Input.player` -> `Player.GetButton(int)`, the ids
from `ReInput.mapping.Actions`; 53 actions, game-notes) and
`Input.GetAxis("Horizontal" / "Vertical")`; `Game/TasInput` binds
`Player.GetButton(string)` / `GetAxis(string)`. This would show a rebind
correctly and a TAS replay's input, but needs each action's name (only
`Crouch`, `Build`, `Horizontal`, `Vertical`, `Mouse X`, `Mouse Y`, `Esc`
are named in the code / game-notes; the rest are read live, never
assumed - rule 7).

Two hazards found while reading, for whoever builds it:
- **Never read through `TheForest.Utils.Input.GetButton*` / `GetAxis`**
  for the overlay: `Game/InputInject` postfixes those, and `TasInput`'s
  recording commits "every name the game has asked for" - an overlay
  asking would add names to a TAS recording the game never read. Read
  Rewired's `Player` directly (as `WorldEvents` does) if source B is used.
- **The bridge's injected input** reaches `Input.GetButton(string)` /
  `GetAxis` only (game-notes `first-input` row) - not Rewired by id, and
  not `UnityEngine.Input.GetKey`. So an e2e check cannot light a
  physical-key tile by injection; it proves the panel draws and costs
  nothing, and a hand test proves the lighting.

**Mouse movement** - Unity 5.6 has no raw mouse delta, and
`Input.mousePosition` is useless while the game locks the cursor
(`VirtualCursor` warps it to the centre, gotcha 1). Candidates:
1. Rewired `Player.GetAxis("Mouse X" / "Mouse Y")` read directly - the
   names are confirmed (MouseLook.LookRotation reads them, IL; game-notes
   `first-input` row), and `TasInput` notes they are per-frame deltas the
   game multiplies by its sensitivity (`SimpleMouseRotator.GetInput`, IL).
   Whether a direct read returns the same value the game's
   `Input.GetAxis` gets on that frame: **bridge check**.
2. `UnityEngine.Input.GetAxisRaw("Mouse X")` - only if the game's
   InputManager asset defines that axis (it throws otherwise): **bridge
   check** (`call static:UnityEngine.Input GetAxisRaw "Mouse X"`).
Recommendation: 1, with 2 as the fallback if the first returns 0 while
the overlay window is open (the plugin holds `InputState.Menu`, which
makes the Menu map exclusive - game-notes *Input states*; what Rewired's
mouse axes read then is unknown).

**When the overlay window is open** the runner's keys go to the window,
not the game (`Game/GameInput` holds `Menu`); physical-key tiles would
still light. Proposed: draw the panel as usual (so Edit HUD shows it
live while you press keys to try it), light nothing while `Cursor.visible`
outside Edit HUD - the same "a cursor on screen means the input is not
the game's" rule `first-input` uses. **Q** below.

## 5. Per-frame cost budget

The HUD's last stutter was a font texture rebuild in OnGUI (gotcha 107,
T-0301), and OnGUI runs several times a frame (gotcha 2). Budget:

- **Sampling in Tick (Update), not in OnGUI**: one `Input.GetKey` per
  tile (native, no allocation; KeyCode overload only, never the string
  one), the scroll delta, the two mouse axes. Stored in a preallocated
  `bool[]` / `float[]` by tile index; a press that lasts one frame is
  latched for a minimum lit time (proposed 50 ms) so a tap shows even on
  a frame the HUD does not repaint.
- **Drawing on `EventType.Repaint` only**: per tile one `GUIStyle.Draw`
  (two cached styles: idle, pressed) with a cached `GUIContent` label -
  about 2 IMGUI draw calls a tile, ~30 for the proposed layout.
- **Text never changes**, so no glyph churn: labels are built once when
  the layout changes. Labels use the UI skin's font at one size, or the
  values' own font with `KeptGlyphs` asked every repaint (gotcha 107)
  if they are drawn large. A number on screen (a mouse distance, a
  counter) would need the same - not in the first version.
- **Mouse trail**: a preallocated ring buffer (proposed 64 points) of
  screen-space positions, drawn in one `GL.Begin(GL.LINES)` pass with the
  `Hidden/Internal-Colored` material, exactly as `MapModule.DrawOverlay`
  draws in OnGUI; fading by vertex colour - no texture, no allocation.
- **Target, to measure on a hand deploy**: 0 bytes a frame
  (`AllocationTracker`), no `Slow tick:` line, no change in the 30 s
  `Perf` line's frame time beyond noise with the panel on vs off, and the
  T-0301 test (16 injected W presses, RivaTuner) with no spike. Off = no
  sampling and no drawing at all.
