# T-0034 Performance: the old world held 30-70 s after a Full load / death reload

Running notes across sessions (docs/harness.md 11a).

- 2026-10-18: forest-researcher, branch worktree-agent-a690d2682f4700764: cause proved live - the A* PathPool keeps the old world's pooled paths (pathHandler / callback / currentR / hTargetNode) until the new world reuses them; PathPool.pool.Clear over the bridge after a Full load: 443.6 -> 327.7 MB and 397 -> 322.7 MB. Build plan below.

## Cause (proved live, v0.24.341 + the census `Paths` tool, Slot 1, 2026-10-18)

`Pathfinding.PathPool.pool` (static `Dictionary<Type, Stack<Path>>`, the
game's A* path pool) outlives a scene load. `Path.OnEnterPool` (decompiled
`Pathfinding/Path.cs` ~290) releases only `path` / `vectorPath`; a pooled
path keeps `pathHandler` (the old path thread's `PathHandler`, a `PathNode`
per graph node, each -> its `GraphNode`), `callback` (-> the old `Seeker`'s
MonoBehaviour), `currentR`, `hTargetNode`, `next` (ABPath also start / end
nodes) until `PathPool.GetPath` pops and `Reset()`s it. The stack is LIFO and
only as deep as the old world's peak, so the old navmesh (~100-130 MB) stays
until the new world has needed as many paths at once - 15 s to minutes, or
never in a quiet world (Creative / Peaceful).

Evidence (bridge, `call static:System.GC GetTotalMemory true`):
- Fresh title load 285 MB; each Full load of `phantom-a` adds ~100-150 MB
  (285 -> 399 -> 446 -> 531, then 413 a minute later); an earlier 20-minute
  session went 294 -> 445 -> 580 -> 714 -> 778 and was still 446 MB 5.5 min
  after the first load.
- `RunScene` 5 s after a Full load: `PathPool.pool` reaches 823k PathNode,
  186k TriangleMeshNode, 6084 NavmeshTile (~111.6 MB) besides the live
  `TriangleMeshNode._navmeshHolders`.
- `call static:Pathfinding.PathPool pool.Clear` 5 s after a Full load:
  443.6 -> 398.9 -> 327.7 MB; again 20 s after one: 397.3 -> 322.7 MB.
  Full GC pause (the bridge's reply time) 112 -> 89 ms.
- `Paths NavmeshTile 6 false` (every static, BFS) at a held moment found only
  the live 6084 tiles: no other static reaches the old graph.

**Second, smaller hold (ours):** `NatureKeeper._lodsFor` / `_lods`
(`src/Game/NatureKeeper.cs` ~492, the tree-LOD cache) keep the last world's
8628 `CoopTreeId` + 8592 `LOD_Trees` (destroyed after a Full load) until the
next Quick-load restore. Nulling both over the bridge: 336.5 -> 314.2 MB
(~22 MB). Seen with `Paths NavmeshTile 12 true` after a spot restart + Full
load: `destroyed x8628: PickupKeeper.NameOf.Target(NameOfItem)(SavestateModule)._nature(NatureKeeper)._lodsFor[] -> CoopTreeId`.

**Unexplained (lead only):** in the first, 20-minute session (an e2e run and
another agent's bridge use before it) `RunScene` credited our static
`DeathHooks.Decide` (-> DeathModule -> every module) with 12168 NavmeshTile
(two old graphs). Not reproduced in two fresh launches. Suspect: the bridge's
`ObjectProbe._handles` keeping a listed component (dev-only), whose dead
fields reach a Seeker / Path. Next time: `call BepInEx_Manager
OverlayPlugin._host._modules[10]._census.Paths TriangleMeshNode 12 true`
names the field.

## Fix (forest-dev)

1. **`Game/PathPoolCleanup.cs`** (or a method in `Game/LeakedThreads` /
   `StaleSubscribers` style; not in `PathfindingWatch`, which is read-only):
   a Harmony **prefix on `AstarPath.Awake`** that, when the switch is on,
   empties `Pathfinding.PathPool.pool` under `lock (pool)` (reflection:
   `FindGameType("Pathfinding.PathPool")`, static field `pool`; read the
   count first as the sum of the stacks' `ICollection.Count`). Not a postfix
   on `AstarPath.OnDestroy`: `Seeker.OnDestroy` -> `ReleaseClaimedPath` ->
   `Path.Release` -> `PathPool.Pool` re-pools old paths for every Seeker
   destroyed after the AstarPath (decompiled `Seeker.cs` 78-90). At the new
   `Awake` the old scene is gone (game-notes: the old AstarPath is destroyed
   before the new one wakes) and the new world has pooled nothing. Clearing
   is behaviour-preserving: `GetPath` makes a new path when the stack is
   empty and `Reset()` sets every field a reused one would get.
   Log once a load when it dropped any: `Pathfinding: dropped n pooled
   path(s) left by the previous world (k this session).` Switch
   `[Fixes] ClearPathPoolOnLoad`, default true, bound next to
   `PruneDeadSubscribersOnLoad` in `SavestateModule` ~172 (memory only, not
   practice-only), description in the same voice.
2. **NatureKeeper**: drop `_lodsFor` / `_lods` when the scene goes (e.g. a
   `ForgetWorld()` called from the same load-finished hook that runs
   `StaleSubscribers`, or check `_lodsFor.Length > 0 && _lodsFor[0] == null`
   before reusing). No log line needed (no runner action).
3. Tests: the count-and-clear helper over an `IDictionary` of
   `Stack<object>` can be pure (`src/Data`) if it is split out; otherwise
   none - the proof is the heap line below.
4. Docs: game-notes *The heap across restores* gets the fix line;
   investigations *Performance / loads* 2 to one line.

## Round 2 (2026-10-18, after the v0.24.342 QA fail)

- **The QA reads were single `GetTotalMemory(true)` calls.** Two in a row
  one frame apart, 15 s after a Full load: 432.9 -> 315.9 MB;
  `WaitForPendingFinalizers` after adds nothing. The first forced
  collection after a load keeps the old world (reached from objects
  queued for finalization - holder not identified; Unity's `Coroutine`
  wrapper fits), the second frees it. `Paths NavmeshTile 10 false` at
  such a moment: only the live 6084 tiles from statics.
- **A real hold of ours: `DrawingsReader._view`.** The 100% tab's 1 s
  refresh searched during the load and cached the old
  `DrawingsInventoryItemView`; once destroyed, its fields kept the old
  `RecastGraph` until the 10 s throttle let it search again. Census:
  `NavmeshTile x6084: DrawingsReader._view(DrawingsInventoryItemView)._inventory(PlayerInventory)._itemViews[41](InventoryItemView)._heldWeaponInfo(weaponInfo).setup(playerScriptSetup).sceneInfo(sceneTracker).birdController(lb_BirdController).rg(RecastGraph).tiles[0]`.
  1.6 s samples (a forced GC each): 433 MB x4 while `_view` was the
  destroyed one, 314 MB right after the re-search. Fix (built on this
  branch): `DrawingsReader.ForgetView()` (view null, search at once),
  called from `SavestateModule.WatchLoads` beside `DeathHooks.ForgetDeath`.
- **The pool clear works** (double reads, 15 s after each of 4 Full
  loads, fresh launch, Slot 1, branch build = v0.24.342 + ForgetView):
  ON 278 -> 291, 300, 303, 305 MB; OFF (`set
  static:ForestOverlay.Game.PathPoolCleanup Enabled false`) 280 -> 291,
  301, 421, 542 MB.
- Census `Paths` now groups the named type's hits by path shape too
  (`<Type> x<n>: <example path>`).
