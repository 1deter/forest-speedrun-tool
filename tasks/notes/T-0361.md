## What the author decided (2026-10-16, the task's answers)

- One switch for the whole overlay: **Raw input** / **Game input**, game
  input the default.
- Rule B: a tile stands for its key's **shipped-default** actions
  (`ReInput.UserData`, Default category 0) and lights whenever one of
  them fires, whatever key the runner bound (the author's Ctrl tile
  lights on his C, his Crouch key).
- The label is **what the input did**, each function named on its own:
  C used to save says Save, used to craft says Craft; M1 tap = Attack,
  held = Heavy attack; and so on. Idle (Only-while-pressed off): the
  tile's functions' names in the pick order (moves > actions > building
  > inventory) until one is performed - the builder says what it shows,
  the author corrects in game.

## What was proved live (v0.24.313 / v0.24.320 + a dev probe build)

Facts in docs/game-notes.md *The default bindings* (actions, two-action
keys, rebinds, axis reads) and *Who performed an input* (this round).

1. 53 actions; two-action keys: E = Take + Build, C = Save + Craft,
   Left Ctrl = Crouch + Batch, M1 = Equip + Fire1, M2 = Combine +
   AltFire. W / S = Vertical +/-, D / A = Horizontal +/-. Wheel: no
   Default-map action. Rebinds live in `Input.player`'s maps.
2. **Context actions are read only in context.** Open world: Take, Save,
   Craft, Build, Batch, Equip, Combine never read. Take read only while a
   `PickUp` had focus, Save only while a `ShelterTrigger` had it.
3. **The reader is on the stack** (dev probe: a postfix after
   InputInject's on `GetButton` / `GetButtonDown` / `GetButtonUp`,
   walking `new StackTrace(1, false)` on a true result, skipping frames
   whose `DeclaringType` is the plugin's or `TheForest.Utils.Input` - the
   Harmony replacement shows as `TheForest.Utils.Input::DMD<...>`).
   Logged readers: Take `PickUp::GetTakeInputDown`; Save
   `ShelterTrigger::Update` (held 1.2 s -> the save-slot screen opened =
   `JustSave`); Jump `FirstPersonCharacter::GetJumpInput`; Run
   `FirstPersonCharacter::Update`; Crouch `GetCrouchInput`, the next
   press `GetStangUpInput`; Fire1 down `PlayerInventory::Update`; Fire1
   up `PlayerInventory::Update`, `HutongGames.PlayMaker.Actions.GetButtonUp::OnUpdate`,
   `playerAnimatorControl+<checkChargeConditions>c__Iterator1::MoveNext`;
   AltFire down `PlayerInventory`, PlayMaker `GetButtonDown`,
   `weaponInfo`. Cost 10-50 us a walk (80 us on a deep PlayMaker stack).
   Bridge `press` / `hold` were attributed too (so TAS replays will be),
   because the probe ran after InputInject's postfix.
4. **Light vs heavy attack** (Axe Plane): pmControl `waitForInput` ->
   `stickAttack` on the press frame; tap -> `waitForCombo` ->
   `waitForInput`; held -> `initCharge` from 0.4 s -> `doCharge` on
   release (animator `doAttackHeavyBool` on). Held AltFire -> `doBlock`.
5. Plugin window open (Edit HUD): Default maps off - W reads Vertical 0,
   Space still Jump (Menu map).

The probe was never committed; its shape is item 2 below.

## Build plan (forest-dev)

1. **`src/Game/GameActions.cs`** - a tile's actions and their state.
   - Bind on first use and when `Input.player` changes (as
     `WorldEvents.PollInput`): delegates for `Player.GetButton(int)`,
     `GetNegativeButton(int)`, `GetAxisRaw(int)`; `ReInput.mapping.Actions`
     -> id / name / categoryId.
   - Default bindings from `ReInput.UserData.keyboardMaps` / `mouseMaps`
     (categoryId 0) -> rows (KeyCode name, action id, sign); mouse element
     3 -> `Mouse0`, 4 -> `Mouse1`. Rule B only: no rebind polling.
   - `bool Active(int action, int sign)`: Rewired by id (a button, or an
     axis sign through `GetButton` / `GetNegativeButton`), ORed with the
     bridge's `InputInject.State`, replaced by `TasInput` while it plays
     (no-alloc accessors, the channel cached per playback). Never call
     `TheForest.Utils.Input.GetButton*` / `GetAxis*`.
   - A status string when unavailable -> game input falls back to raw,
     the reason shown in the Input overlay section.
2. **`src/Game/ActionReaders.cs`** (new) - who performed it.
   - Its own Harmony id; installed while the overlay is shown in game
     input, unpatched otherwise. Postfixes on `TheForest.Utils.Input`
     `GetButtonDown`, `GetButtonUp`, `GetButton`, `GetButtonAfterDelay`,
     `GetButtonPress`, `IsPastButtonPress`, ordered **after**
     InputInject's (`HarmonyAfter` / priority), so bridge and TAS values
     count.
   - Early out unless `__result` is true and the name is one of the
     shown tiles' actions (a small array of watched names; no dictionary
     per call).
   - Walk only on Down, Up, AfterDelay, Press, and on `GetButton` during
     the first 3 frames after the action went active (Crouch was read
     only through `GetButton` in `GetCrouchInput`). Never per held frame.
     At most 8 walks a frame; dedupe (action, reader) per frame.
   - The walk: `new StackFrame(i, false)` from i = 1 up to the first
     `DeclaringType` that is neither the plugin's nor
     `TheForest.Utils.Input` (that skips the DMD frame; a true result
     from `Input.LateUpdate`'s own `GetButtonAfterDelay` call ends in
     Unity, not game code - ignore it). A compiler-generated nested type
     (`<...>c__Iterator`, closures) -> its `DeclaringType`. Result: (type
     full name, method name), interned once per new pair.
   - Publishes per action: the last reader's function id and its frame.
     Allocation on press frames only (the walk), none otherwise.
3. **`src/Data/ActionFunctions.cs`** (pure) + tests - reader -> label.
   - Rows: type, method (or any), action (or any), label, generic flag.
     A specific row beats a generic one on the same frame; the newest
     press wins across frames. An unknown reader -> the action's idle
     word, plus `ActionReaders: unnamed reader <Type::Method> for <Action>`
     logged once per pair, so report zips grow the table.
   - Seed from the ilscan lists (`refs TheForest.Utils.Input::GetButtonDown`
     141, `GetButtonUp` 14, `GetButtonAfterDelay` 27, `GetButtonPress` 1;
     also `GetButton`): at least every reader of the default-layout
     actions plus Take, Save, Craft, Build, Batch, Equip, Combine.
     Examples (builder's words, the author corrects): `ShelterTrigger`
     Save -> Save, Take -> Sleep; `PickUp` Take -> Take; `LogHolder` Craft
     -> Add log; `Fire` / `Fire2::UpdateCooking` Craft -> Cook;
     `Fire2::UpdateFueling` -> Add fuel; `Fire2::UpdateNotLit` -> Light;
     `MultiHolder::LogContentUpdate` / `RockContentUpdate` /
     `StickContentUpdate` -> Add log / rock / stick; `activateClimb` ->
     Climb; `activateZipLine::GrabZiplineUpdate` -> Zipline;
     `Craft_Structure` -> Build; `InventoryItemView` Equip / Combine /
     Batch -> Equip / Combine / Batch; `FirstPersonCharacter::GetCrouchInput`
     -> Crouch, `::GetStangUpInput` -> Stand up, `::GetJumpInput` -> Jump,
     `::Update` Run -> Sprint; `BowController` Fire1 -> Shoot. Read each
     reader's code (game-src) before naming it - the read sits next to
     what it does.
   - Generic readers (`PlayerInventory::Update`, `weaponInfo::Update`,
     `HutongGames.PlayMaker.Actions.*`, `playerAnimatorControl*`,
     `CameraMouseEvents`) -> refined by the player's FSM (item 4).
   - Tests: specific beats generic on one frame, newest press wins,
     iterator type folding, unknown -> idle word, idle label order (Ctrl
     "Crouch / Batch", E "Take / Build", C "Save / Craft", M1 the attack
     word first).
4. **pmControl refinement** (per frame only while a Fire1 / AltFire tile
   is held or lingering): `LocalPlayer.ScriptSetup.pmControl.ActiveStateName`
   through FastField (the state's own `Name` string - compare, never
   build). Pure map in `ActionFunctions`: `stickAttack`, `stickAttack2`,
   `axeAttack`, `normalAxeAttack*`, `rockAttack*`, `chooseRandomAttack`,
   `waitForCombo*` -> Attack; `initCharge`, `doCharge` -> Heavy attack
   (from 0.4 s, the charge); `doBlock`, `blockHit` -> Block. Only
   `stickAttack`, `waitForCombo`, `initCharge`, `doCharge`, `doBlock` were
   seen live; the FSM's other attack states (`overheadAttack`,
   `axeSmashAttack*`, `rockSmashAttack`, `spearAttack`, `startSpearThrow`,
   `drawBow`, `releaseBow`, `shootFlareGun`, ...) are named from
   docs/fsm/player-controlFSM.txt and checked by forest-tester. The
   label keeps the strongest state seen during the press (Heavy attack
   over Attack), so a heavy press ending in `waitForCombo` still says
   Heavy attack.
5. **`src/Modules/InputOverlayModule.cs`**: `[Inputs] Source` (`Game` |
   `Raw`, default Game) registered as a HUD profile entry (a profile from
   before T-0361 gets Game: say so in the changelog); a segmented control
   **Game input / Raw input** in Edit HUD's Input overlay section; one
   log line per change (`Inputs: source game input` / `raw input`). Per
   tile (`TileState`): its default actions (GameActions), lit = any
   `Active`; label = the performed function from the press until release
   plus a short linger (builder picks, e.g. 0.75 s), then the idle label;
   cached `GUIContent` per label id (no per-frame strings). A key with no
   default action: dimmed key name, its Edit HUD row says "no game action
   on this key". Edit HUD (window open, Default maps off): tiles light
   from the raw key, idle labels. Mouse box: the Mouse X / Y actions;
   wheel raw. Movement tiles: Forward / Back / Left / Right by sign, no
   reader needed.
6. log-catalogue (`Inputs:`, `ActionReaders:`, `GameActions:` with
   `Meaning:` lines), docs/areas/plugin.md feature row.
