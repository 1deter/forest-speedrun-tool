### What was proved live (v0.24.313, the author's install, SendInput keys)

Facts now in docs/game-notes.md *The default bindings* (second paragraph).

1. **53 actions** from `ReInput.mapping.Actions` (id, name, type, action
   category). The shipped Default maps bind **some keys to two actions**:
   E = Take + Build, C = Save + Craft, Left Ctrl = Crouch + Batch, mouse
   left = Equip + Fire1, right = Combine + AltFire. W / S = `Vertical`
   +/-, D / A = `Horizontal` +/-. The wheel has no Default-map action
   (only `ScrollY` in the Menu map). Side buttons unbound.
2. **Runners' rebinds are live, and the author has some.** The game
   saves rebinds to PlayerPrefs and loads them into `Input.player`'s
   maps. On this install Crouch is on **C**, Inventory Tab, Book F,
   Lighter Q, Craft V, Save E. Left Ctrl held: `GetButton("Crouch")`
   False, `GetButton("Batch")` True. C held: Crouch True, Save / Craft
   False. Rewired never reads `UserData` (the shipped defaults) at run
   time.
3. **Axis actions by sign**: S held -> `GetAxisRaw("Vertical")` -1,
   `GetAxis` -1 (no ramp: digital gravity / sensitivity 1000, snap),
   `GetNegativeButton("Vertical")` True, `GetButton` False; 0 / False on
   the release frame.
4. **While the plugin's window is open** (Menu state; Edit HUD is drawn
   with the window open) the Default maps are off: W read `Vertical` 0,
   Space still read Jump True (the Menu map binds Space to Jump).
5. **Rebind signal**: static `InputMappingIcons.Version` (int, 6 here) is
   incremented at the end of every `RefreshMappings`, which
   `InputMapping.LoadAllMaps` calls after it reloads the maps (IL).
6. Already known: the bridge's `press` / `hold` / `axis` reach only
   `TheForest.Utils.Input.*` (InputInject postfixes), never Rewired by
   id; a TAS replay replaces those same reads (TasInput). So "a TAS
   replay's inputs show too" needs the overlay to ask TasInput /
   InputInject for their values: reading Rewired alone shows the
   player's hands during a replay.

### The open question (parked for the author, see the task's question)

Fact 2 changes what option 1 looks like. Which action does a key's tile
show in game input?

- **A. What the key does now in this runner's game** (the live maps).
  Here: the Ctrl tile shows Batch, the C tile Crouch. Game input then
  differs from raw input only for keys with no action (dead), for a
  second key bound to the same action, for TAS replays and for bridge
  input.
- **B. The key's shipped default** (`UserData`), as option 1 was
  written ("the key's default action"). The Ctrl tile shows Crouch on
  every install and lights when the action fires, so here it lights
  on C, and the C tile shows Save. A rebind follows the action, but the
  label can name a key the runner no longer uses for it.

Either way: **which of a two-action key's actions** does the tile show?
The plan below takes one action per tile, chosen by action category
(moves 6 > actions 2 > building 3 > inventory 4 > the rest, then map
order): Ctrl = Crouch, E = Take, M1 = Fire1, M2 = AltFire, C = Save (B).
The tile lights on that action only, so label and light agree.

### Build plan (forest-dev, once the author picks A or B)

1. **`src/Game/GameActions.cs`** (new; every Rewired name lives here).
   - Bind on first use and again when `Input.player` changes (as
     `WorldEvents.PollInput` does): delegates `Func<int,bool>` for
     `Player.GetButton(int)` and `GetNegativeButton(int)`, and
     `Func<int,float>` for `GetAxisRaw(int)`. `ReInput.mapping.Actions`
     gives id / name / type / categoryId; bind properties with Public |
     NonPublic.
   - Bindings table: rows of (key name, action index, sign) for the
     Default map category (`categoryId` 0) only, keyboard (`keyCode`
     -> `KeyCode.ToString()`) and mouse (element 3 -> `Mouse0`, 4 ->
     `Mouse1`; 0 / 1 are the look axes). For rule A, from
     `Input.player.controllers.maps.GetAllMaps(ControllerType.Keyboard /
     Mouse)` -> `AllMaps`; for rule B, from `ReInput.UserData.
     keyboardMaps` / `mouseMaps` -> `actionElementMaps`. Rule A
     re-reads when `InputMappingIcons.Version` changes
     (`FastField.Static<int>`, polled once a second at most, never
     per frame through reflection).
   - `bool Held(int action, int sign)`, `float Axis(int action)`, in
     this order:
     1. `TasInput.Current == Blocking` -> false / 0.
     2. `Playing` -> the replay's value for the action's name. Add a
        no-alloc accessor to `TasInput`, e.g.
        `TryReplay(string name, out bool held)` / `TryReplayAxis`, with
        the channel looked up once per playback (`FindButton` /
        `FindAxis`) and cached per action. An axis tile uses the
        sign of the replayed axis value.
     3. Else Rewired (`GetButton` for sign +1 on a button or a positive
        axis, `GetNegativeButton` for -1), ORed with
        `InputInject.State.Held(name, frame, now)` (axes:
        `State.TryAxis`, sign checked), only when `State.Any`.
   - **Never** call `TheForest.Utils.Input.GetButton*` / `GetAxis*`:
     InputInject counts every name read (`input seen`), and a TAS
     recording would pick up the overlay's reads as the game's.
   - One log line when bound, and again on a Version change:
     `GameActions: 53 actions, N keyboard + M mouse bindings (live|default)`.
     Then log-catalogue + `Meaning:`.
   - Unavailable (a game update, Rewired not ready) -> a `Status`
     string; the module shows it in the Input overlay section, and game
     input falls back to raw reads with that reason visible (check 13).
2. **`src/Data/InputActions.cs`** (pure) + tests.
   - Input: the binding rows plus each action's name and category.
     `Resolve(key)` -> (action index, sign) or none, by the category
     order above, then row order.
   - `Label(actionName, sign)`: Vertical + "Forward" / - "Back",
     Horizontal - "Left" / + "Right"; otherwise a short table
     (builder's words, memory *wording no sign-off*: Fire1 "Fire",
     AltFire "Alt fire", RestKey "Rest", SurvivalBook "Book", ItemSlot1-4
     "Slot 1"-"4", WalkyTalky "Walkie", checkArms "Arms", birdOnHand
     "Bird"); otherwise the action name verbatim.
   - Tests: W / S / A / D signs, Ctrl -> Crouch over Batch, E -> Take over
     Build, Mouse0 -> Fire1 over Equip, a key with no row -> none, a
     live table (C -> Crouch) against the defaults, labels.
3. **`src/Modules/InputOverlayModule.cs`**:
   - `[Inputs] Source` (`Game` | `Raw`, default **Game**), registered
     with `HudWidgets.RegisterProfileEntry` like `OnlyPressed`. A
     profile written before T-0361 has no entry and gets Game (the
     author's default): say so in the changelog.
   - Edit HUD, Input overlay section: a segmented control **Game input
     / Raw input** (author's words) at the top, and one log line per
     change: `Inputs: source game input` / `Inputs: source raw input`.
   - Tile label in game input: `InputActions.Label` of the tile's
     action; a key with no action is drawn dimmed with its key name,
     and its Edit HUD row says "no game action on this key" (check 13).
     `TileState` gains the action index / sign; rebuilt on `Reload`, on
     a source change and when GameActions' bindings change (no
     per-frame strings: cached `GUIContent`).
   - Tick in game input: `GameActions.Held(action, sign)` per key tile.
     **In Edit HUD** the window is open, the Default maps are off
     (fact 4) and nothing would light, so tiles light from their raw
     key there, as today.
   - Mouse box in game input: `GameActions.Axis` of Mouse X / Mouse Y
     (the same numbers as Unity in play, game-notes; a TAS replay's
     look then shows). Raw: unchanged. Wheel: raw in both sources (no
     Default-map action).
   - Zero allocation per frame (lint alloc). Off = nothing read.
4. Docs: docs/areas/plugin.md feature row (Input overlay: + GameActions,
   InputActions); docs/log-lines.md via the catalogue.
