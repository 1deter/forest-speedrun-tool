# T-0121 Check logs in the inventory: repairing a broken building part takes the logs from the store

Running notes across sessions (docs/harness.md 11a).

- 2026-10-19: Checked live (forest-researcher, bridge, v0.24.363, a Creative save, near (457, 77, -8)). Passes for a foundation-type building with the repair tool in hand; a plain building part takes no logs, same as vanilla. Found T-0431: with logs stored, `Equip` refuses right-hand items.

## How the game repairs with logs (IL + live)

- Logs are needed only when pieces have **collapsed**:
  `CalcMissingRepairLogs = _collapsedLogs / 3 - _repairLogs` on both
  `BuildingHealth` and `FoundationHealth`. `_collapsedLogs` grows when a
  `BuildingHealthChunk` collapses (+1 per active renderer tagged `Log`) or a
  `FoundationChunkTier` breaks (+1 per renderer). A part that is only damaged
  needs repair material (sap), not logs. This backs up sxczurass's "repairs
  use the repair tool, not logs". The log cabin prefab's chunk logs are
  untagged, so collapsing its chunk gave 0 logs (live).
- Two `RepairTool` components exist. One is on the held log
  `.../ptemp/LogHeld1`: in vanilla, carrying a log at a broken-down part and
  pressing Take adds it, with no repair tool. The other is on
  `RepairToolHeld/collide` (`LocalPlayer.RepairTool`). Both run
  `RepairTool.Update`, where Take calls `Inventory.RemoveItem(78)`.
- `OnGrabberEnter` targets a plain `BuildingHealth` only while
  `!Logs.HasLogs`, and a `FoundationHealth` with logs when logs are missing.
  So a plain part missing logs can never take one, in vanilla or with the
  mod.

## Live evidence (2026-10-19)

A `LogCabinBuilt` (FoundationHealth + BuildingHealth) was instantiated by the
bridge, with `FoundationHealth._collapsedLogs` = 3 (1 log missing).
- Vanilla, mod off, 1 log in the arms (`Lift`), no tool: LogHeld1's RepairTool
  targeted the cabin. `press Take` -> `_logs` 1 -> 0, missing 1 -> 0.
- Mod on, 3 stored, no tool: `press Take` did nothing (LogHeld1 is hidden,
  so its RepairTool never runs).
- Mod on, 3 stored, repair tool equipped (with `_logs` set to 0 for the
  equip, see T-0431): the target was set, `HudGui.AddIcon` was on, and
  `press Take` logged
  `Logs in the inventory: stored 3 -> 2 (LogControler.DMD<...PutDown> <- PlayerInventory.DMD<...RemoveItemNF> <- PlayerInventory.RemoveItem <- RepairTool.DMD<...Update>)`.
  Missing went 1 -> 0, and the HUD went from `Logs 3 / 5` to `2 / 5`
  (bridge shots `t0121-before-take`, `t0121-after-take`).
- `WallBuilt` (plain BuildingHealth), `_collapsedLogs` = 3: focused but not
  targeted, both with the mod (2 stored) and in vanilla (2 in the arms).
  Take changed nothing either way.

## Differences from vanilla (for the author / runners)

- With the mod on, adding logs to a broken-down part needs the **repair tool
  in hand**. Vanilla needs only the carried log.
- With logs stored, the repair tool cannot be equipped (T-0431), so today it
  works only if the tool is in hand **before** logs are stored.

## Post-release check (forest-tester)

Do this after T-0431 ships; before that, equip the repair tool before storing
logs.
1. Turn the mod on, store 2 logs (`Inventory.Logs.Lift` x2), and equip the
   repair tool (`Inventory.Equip 257 false`; add it first with
   `AddItem 257 1 true false null` if it is missing).
2. Instantiate `Prefabs.Instance.Constructions._blueprints[10]._builtPrefab`
   (LogCabinBuilt), move it in front of you, and set
   `FoundationHealth._collapsedLogs 3`.
3. Look at its wall (`Grabber.FocusedItemGO` is a child of the cabin), then
   `press Take`. Expect a `Logs in the inventory: stored 2 -> 1 (... RepairTool...Update)`
   line, `FoundationHealth.CalcMissingRepairLogs` back to 0, and the HUD
   showing `Logs 1 / 5`.
4. Clean up: destroy the cabin, `_logs 0`, mod off, `RemoveItem 257 1 false false`.
