## The plan as written in session 1 (kept for the reasoning)

4. **Arming and the frame step move into RunTimerModule.** API:
   `Arm(Segment, ArmSource, anchor, cause)`, `Abort(why)`, `Disarm(why)`,
   `Advance()` (F12: move the `run.manualSplit` and `run.abort` hotkeys,
   same ids), `Resume(CheckpointState)`, `PracticeOn` (F9's state, set by
   PracticeRunModule: Timing = RunTiming.TimingOn), `Hold` (true while the
   replay camera plays: no evaluation, `_eventsSeen` follows). Events, in
   the order the module now acts: `GameEvent(index, pos)` per event
   *before* the gate (RecordReplayEvent needs it there, exactly), `Started`,
   `SplitTaken(row, t, byHand)`, `EndBlocked`, `FinishDue` (practice does
   FinishRun as today), `Dropping(why)` before every abort (KeepFailed +
   RecordUnfinished stay practice-side). Keep the frame order: either
   PracticeRunModule calls `_runTimer.Step()` at the point its Tick
   evaluates today (after LeaveLevel / RunModeEnded / the replay hold /
   the segment-edit re-arm, before the delta and the lines), and
   RunTimerModule.Tick steps only when no driver claimed the frame (the
   run file); or the pre-work moves too. Do not let RunTimerModule tick
   first on its own: a level left would be evaluated for a frame.
   Tests: the event order (GameEvent before the gate, Dropping before the
   abort) as a pure "driver" class if it can be one.
5. **The splits panel moves into RunTimerModule** (the rest of
   PracticeRunModule.Splits.cs: config section `Splits` with the same keys
   and `Runs.RunnerName` / `Runs.LocalRunnerId`, RegisterSplitsProfile, the
   panel, timer glyphs, drag / resize, docked rows, DrawHudEditor's splits
   rows). Registered before `practicerun`, the host draws the Edit HUD
   rows in the same order (splits, then the results panel's). The results
   panel (Results.cs) shares `SplitPalette`, `_cellStyle`,
   `_colourStyles`, `_timeDecimals` - move those to one Core place both
   use. The comparison comes through a Core interface PracticeRunModule
   implements (stats, compare splits and name, watching + its clock and
   times, results showing, started / finished counts, PB chance and
   playtime lines). Decide with the author (rule 5) whether the attempt
   store, the own-PB / last / average / best-segments comparisons and the
   upload of a finished run belong to the timer of record (a run file with
   no practice pack still needs a PB to race) - REVIEW.md *Target
   architecture* puts "timer and split state machines" in Core and ghosts
   in the practice pack, so the proposal is: yes, they move with the panel;
   runner (site) and LiveSplit comparisons stay practice-side.
6. HUD lines Run / LRT / Next / Last follow the timer (Delta is the
   ghost's: practice). Then update docs/areas/plugin.md's feature map,
   docs/quality.md's row, and set the task `built`.
