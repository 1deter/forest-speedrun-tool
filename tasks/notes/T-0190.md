# T-0190 Render-thread crash on a texture sub-upload (d3d11 read of 0xec): plugin or game?

Running notes (docs/harness.md 11a). Verdict: **the engine's** - a font
texture reset hitting a texture Unity 5.6 registered with a null D3D
resource after a failed `CreateTexture2D`; no plugin texture path can send
that command. Write-up: docs/game-notes.md *The render-thread crash on a
font texture reset*.

Both d3d11 dumps are the same to the byte where it matters:

- **Faulting thread = UnityGfxDeviceWorker**: `RunThreadWrapper` ->
  `GfxDeviceWorker::Run` -> `RunCommand+0x2a07` ->
  `GfxDeviceD3D11Base::UploadTextureSubData2D+0x5a` ->
  `TexturesD3D11::UploadTextureSubData2D+0x159` (the return from
  `ID3D11DeviceContext::UpdateSubresource`, vtable +0x180) -> d3d11.dll+0x152a5a:
  `f7 82 ec 00 00 00 00 00 40 00` = `test dword [rdx+0xec], 0x400000`, rdx = 0
  (UpdateSubresource's `pDstResource`).
- **The command**: TextureID 0x11a4 (10-04) / 0x1244 (10-05), x 0, y 0,
  256 x 256, format 1 (Alpha8), 0x10000 bytes, `0x41` on the stack
  (DXGI_FORMAT_A8_UNORM = 65). A stale `TexturesD3D11Base::UploadTexture2D+0x396`
  just above rsp: a full texture upload ran at the same depth just before.
- **Main thread**: `PlayerLoop -> PlayerRender -> GfxDeviceClient::BeginFrame
  -> WaitForPendingPresent -> GfxDeviceWorker::WaitForEventWithMessagePump`
  (waiting for the worker). `RTSSHooks64.dll` on its stack in 10-05.
- **UnityPreload thread** idle (`PreloadManager::Run` waiting): no async
  scene load in flight at the fault, in both.
- Modules: the same 128-130 in all three dumps; third-party D3D hooks in
  all three: `RTSSHooks64.dll` (RivaTuner), `gameoverlayrenderer64.dll`
  (Steam overlay), NVIDIA `nvwgf2umx.dll`.
- No log text in the dumps (stacks only; searched for `d3d11`, `failed`,
  `DXGI`, `Load timing`).

## What sends that command (player PDB + exe disassembly, capstone)

- `UploadTextureSubData2D` is `GfxDevice` vtable slot 120 (+0x3c0). Every
  `call/jmp [reg+0x3c0]` in TheForest.exe outside the D3D9/12/GLES/VK
  devices: `FontImpl::AddCharacterToTexture`, `FontImpl::ResetCachedTexture`,
  `BaseVideoTexture::UploadTextureData`, plus the client/worker relay.
  **`Texture2D.Apply`, `LoadRawTextureData`, `SetPixel(s)`, `ReadPixels`
  never send it** (they go through `UploadTexture2D`, a full create).
- `FontImpl::ResetCachedTexture` clears a dynamic font's whole atlas:
  zero buffer of w*h, `UploadTextureSubData2D(id, zeros, w*h, 0, 0, 0, w, h,
  Alpha8, cs)` - exactly the dumps' command. On D3D11 it skips the re-create
  when the texture already has that size and `Texture2D+0xd5` (uploaded) is
  set; else `InitTexture` + a full upload first. Callers: `CacheFontForText`
  (atlas full), `AwakeFromLoadImpl` (a font loaded with a scene),
  `CreateDynamicFont`, `LoadAllFonts`, `SetFontNames`.
- `TexturesD3D11::UploadTextureSubData2D`: `QueryNativeTexture(id)`; no
  entry -> return (no crash); an entry -> `UpdateSubresource(entry->m_Texture)`.
  So the crash needs **an entry whose resource is null**.
- `TexturesD3D11Base::UploadTexture2D`: when `ID3D11Device::CreateTexture2D`
  (vtable +0x28) fails it logs `d3d11: failed to create 2D texture id=%i
  width=%i height=%i mips=%i dxgifmt=%i [D3D error was %x]` and **carries
  on**: the SRV create fails too, then it allocates the `D3D11Texture` entry
  with the null texture and `TextureIdMap::UpdateTexture(id, entry)`. The
  next sub-upload to that id is the crash.
- `TexturesD3D11Base::DeleteTexture` releases and `TextureIdMap::RemoveTexture`s
  - a destroyed texture leaves no entry (a later sub-upload returns early).

The one plugin-driven route to the crashing command is IMGUI text: drawing
text in sizes / styles the Arial atlas lacks makes Unity reset or grow it.
The game's own NGUI labels do the same with their dynamic fonts
(`NGUIText.Update` / `Prepare` -> `Font.RequestCharactersInTexture`,
`UILabel.OnEnable` -> `Font.textureRebuilt`; ILScan). A reset on a healthy
texture is harmless (live, below); it only crashes on a texture whose create
had already failed.

## Live (bridge, v0.24.269, title screen, 2026-10-10)

- `GUISkin.current` = `GameSkin`; `.font` = `Arial`, `dynamic` True,
  `material.mainTexture` = `Font Texture` 256 x 256 **Alpha8** - the dumps'
  texture shape.
- `Font.RequestCharactersInTexture(62 chars, 120, Normal)` on it: atlas
  256 -> 1024, native pointer 1781699168 -> 6606032928 (re-created); no
  crash. The reset / grow path runs on demand from managed code.
- **Unity's own errors are in no kept log.** `Debug.LogError("T0190 ...")`
  and a native error (`SceneManager.LoadScene("T0190-no-such-scene")`,
  "couldn't be loaded ...") wrote nothing to LogOutput.log; with
  `Logger.Listeners[0].WriteFromUnityLog` (DiskLogListener) set true they
  did (`[Error  : Unity Log] ...`), set back false after. BepInEx.cfg has
  `[Logging.Disk] WriteUnityLog = false`; the game writes no
  `output_log.txt`. And `Application.CallLogCallback` (UnityEngine.dll,
  ilspycmd) hands a message from another thread only to
  `s_LogCallbackHandlerThreaded` (`logMessageReceivedThreaded`) - the d3d11
  line comes from the render thread, so BepInEx's main-thread listener would
  miss it even with WriteUnityLog on.

## Why the create failed: not in the evidence

256 x 256 A8 is a valid, tiny texture: `CreateTexture2D` fails for it only
when the device is gone (DXGI_ERROR_DEVICE_REMOVED / hung - a driver reset)
or out of memory. The `[D3D error was %x]` line would say which, and it was
never logged anywhere kept. The author said the PC "has been acting up"
around 10-05 (docs/ui-redesign.md at 93c13b8). Not reproducible over the
bridge (it needs a failing device).

## Follow-ups (not built here - scope: a src fix only if the plugin causes it)

- Proposed T-new: the plugin subscribes to `Application.logMessageReceivedThreaded`
  and writes Unity errors (rate-limited, render-thread ones included) to its
  log, so the next crash's session log names the D3D error. Needs the
  author's yes: it adds a log stream to every report zip.
- Idea: keep the session log beside a new crash folder at the next launch
  (the 10-04 / 10-05 logs were lost to the 3-session rotation).
