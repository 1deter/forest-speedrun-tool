# T-0111 Run mode: the report hashes the game file on disk, not the loaded assembly

Running notes across sessions (docs/harness.md 11a).

- 2026-10-18: 2026-10-18 researcher: cause measured live; build plan below (forest-dev).

## Cause and evidence (live, v0.24.348, x64, 2026-10-18)

- Today `RunIntegrity.StartHashing` SHA-256s `Managed/Assembly-CSharp.dll`
  on disk. The bytes Mono runs are a separate in-memory copy
  (`raw_data_handle` 0: the file is read into memory, not mapped), so a
  file changed before launch and put back after - or a loader that feeds
  Mono patched bytes - is not seen by the file hash.
- **The author's option A as worded (HashTypes on every launch) fails his
  perf condition.** Measured (docs/game-notes.md *The loaded game code in
  memory*): a pass is 275-371 ms of CPU and ~42.7 MB of garbage - fine on
  a worker on the title screen - but it **keeps ~28-30 MB for the whole
  session** (runtime reflection cache: title heap 39.1 -> 68.6 MB, in a
  loaded Slot 1 279.0 -> 306.5 MB), and **every full GC in play gets
  ~10 ms longer (69-71 -> 79-81 ms, +14%)**; title 8 -> 13 ms.
- **The loaded image can be hashed directly at no lasting cost.**
  `asm.ManifestModule` field `_impl` (internal IntPtr, read over the bridge)
  is the `MonoImage*`; x64: `raw_data` pointer at +16, `raw_data_len`
  uint32 at +24. Read from outside the process: 8,231,936 bytes starting
  `MZ`, SHA-256 = the file's = `3fcb3958...` (KnownGameHashes[0]). So the
  loaded-image hash of an untouched game **equals the known file hash** -
  no new constant, the site's judging is unchanged.
- The type table of the loaded code (with our Harmony patches applied)
  equals `steam-types.txt` line for line, so the existing "changed game"
  path (type table -> site names the changed types, red) works as is.

## The fix (Game/RunIntegrity, Data/RunReport; ~60 lines + tests)

1. `RunIntegrity.StartHashing` (same worker thread): new
   `LoadedImageHash(Assembly asm, out string why)`:
   - `IntPtr.Size != 8` -> null, why "32-bit game" (layout not seen live).
   - `typeof(Module).GetField("_impl", Instance|NonPublic)` on
     `asm.ManifestModule`; 0 -> null.
   - `raw = Marshal.ReadIntPtr(img, 16)`, `len = (uint)Marshal.ReadInt32(img, 24)`;
     plausible only if raw != 0, 1 MB <= len <= 256 MB, the first two bytes
     are `MZ` and the `PE\0\0` signature sits at `e_lfanew` (< len).
   - SHA-256 over the bytes in 64 KB chunks: one reused `byte[65536]`,
     `Marshal.Copy(raw + off, buf, 0, n)`, `sha.TransformBlock`, then
     `TransformFinalBlock(buf, 0, 0)` - no garbage beyond the buffer.
   - every exception -> null with the message.
   - `CheckLoadedImage()` (static, no args, for the bridge): "<loaded
     hash> / <file hash>", main thread, ~50 ms.
2. `GameHash` = the loaded-image hash; the file hash is read too. When the
   image hash is null, fall back to the file hash (today's behaviour) and
   record why. Type table (`HashTypes`) still only when `GameHash` is not a
   known build - unchanged.
3. `Data/RunReport` (tested): `GameFileHash` (written `gamefile = ...`
   only when it differs from `game`), `GameFrom` (`gamefrom = file: <why>`
   only for the fallback). Findings: `game` unknown stays the existing
   NOT OK line; add `Note  The game's file on disk is not the code that
   was loaded (<12 hex>).` when `gamefile` differs, and `Note  The game's
   code was checked from its file, not from memory (<why>).` for the
   fallback. Parse both keys. Old reports: no keys, same findings.
4. Log line: `Run mode: game code is the known Steam build (Assembly-CSharp
   3fcb3958d5c6, loaded image)` / `(..., from the file: <why>)`, plus
   one warning line when the file and the loaded image differ.
   `scripts/log-catalogue.py` + docs/log-lines.md Meaning.
5. Site (`Attempts.JudgeReport`): show the two new notes as `note`
   findings (no colour change); `RunReport` is linked, so Parse covers it.
6. Docs: docs/run-mode.md - replace the *Decisions* bullet "The report
   reads the game's file on disk at startup, not the loaded assembly" with
   the loaded image (and why HashTypes is not run every launch: the
   numbers above); the RunIntegrity header comment.

Tests: RunReport Format/Parse round trip with and without `gamefile` /
`gamefrom`; Findings for each (known loaded + other file = OK + Note;
unknown loaded + known file = NOT OK; fallback = Note); `Clean` unchanged
(it reads `game` only). If the plausibility check goes in `Data/` (head
bytes + length -> bool), test MZ / PE / length cases.

## Live checks (forest-tester, after release)

1. Fresh launch, title screen: log has `Run mode: game code is the known
   Steam build (Assembly-CSharp 3fcb3958d5c6, loaded image)`; no `gamefile`
   line in a run report.
2. Perf: `Perf (30 s):` lines on the title screen show no new hitch; in a
   loaded Slot 1, `call static:System.GC GetTotalMemory true` twice and
   `call static:System.GC Collect` x3 match a build without the change
   (~279 MB, ~70 ms here) - the pass must keep nothing.
3. Memory, not disk: add a bridge entry `RunIntegrity.CheckLoadedImage()`
   (static, no args) returning "<loaded hash> / <file hash>". On a
   disposable install at the title screen, back up
   `Managed/Assembly-CSharp.dll`, overwrite it with a copy that has one byte
   changed near the end (if Windows refuses, the file is held open - note
   it and skip), call `CheckLoadedImage`: the loaded hash stays
   `3fcb3958...`, the file hash changes. Put the file back, sizes checked.
