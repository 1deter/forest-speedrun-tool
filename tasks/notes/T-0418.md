# T-0418 Restore: re-create a dropped copy that was there at the capture but despawned on the game's own timer since

Running notes across sessions (docs/harness.md 11a).

- 2026-10-18: Researched live (forest-researcher, bridge, v0.24.356, Slot 1 at (428, 78, -4)): cause proved, build plan below. Game facts: docs/game-notes.md *A dropped copy's despawn timer, and making one again*.

## Cause (proved live)

- `FakeDrop 57 / 53 null` -> `Stick_Dynamic(Clone)` #-125484, `Rock_Dynamic(Clone)`
  #-125534, each with `destroyAfter` (60 s, `destroyDistance` 20: after 60 s,
  every 10 s, destroyed while the player is over 20 m away). `capture t418a`
  wrote both in its `dropped` line (`-125484:57@431.7042,76.11679,-3.288275@...`).
- Player teleported 28 m off: both handles `destroyed` within 25 s (60 s after
  the drop). Back, `restore t418a`: `find _Dynamic` 0; the done line had
  `removed 0 ...`, `pickups put back 0`, and the listing said `every world
  pickup matches the capture` (it only lists extras). **A Quick load does not
  bring back a copy that despawned since the capture.**
- Same gap, second way in: restoring an *older* savestate removes a copy made
  after *its* mark (T-0411). Restoring a newer capture that had the copy then
  finds it gone. Same fix.

## What makes an identical copy (proved live)

- `call static:UnityEngine.Object Instantiate <Items[35]._pickupPrefab>` (the
  `Stick_Dynamic` Transform; Rock: `Items[32]`) gave a copy with the same
  components, children, scale, tag, layer and `PickUp` fields as the FakeDrop
  copy. `_destroyTarget` was the new root, `destroyAfter` invoking.
  `PickUp.Collect` on it: stick count 0 -> 1.
- **Use `Instantiate(prefab, pos, rot)`, not FakeDrop + move.** FakeDrop is the
  same Instantiate (decompiled `PlayerInventory.FakeDrop`), plus a drop sound at
  the player and a spawn in front of the player. A copy made elsewhere and then
  moved keeps its velocity: one moved at -38 m/s fell through the ground. Made
  at the captured pose with zero velocity, it rested within 0.02 m of the pose.
- **The re-made copy has a new, lower id, so the next Quick load of the same
  capture removes it.** Live: `restore t418a` with both re-made copies ->
  `removed 2 item(s) made since the capture (Stick x1, Rock x1)`. Without a
  remap the restores would churn: removed 1 + re-made 1 on every load. And a
  re-made copy that was taken would be forgotten by the TakenList clean-up,
  leaving it hidden and never re-made.

## Fix (build plan for forest-dev)

All in `PickupKeeper.MirrorRoots` (src/Game) and `Data/DroppedPoses`. It is
Quick-load only, same world only: the existing `poses != null` condition.

1. **Capture flag** (`CaptureDropped`): for each recorded root whose instance id
   is negative (made at runtime) and whose name is
   `ItemById(item)._pickupPrefab.name + "(Clone)"`, mark the pose as
   re-creatable. Resolve `ItemDatabase.ItemById` and `Item._pickupPrefab`
   (Transform) by reflection in src/Game. `InventoryReader` already resolves
   `ItemById` (line ~605); reuse it or the same lookup.
2. **Format** (`DroppedPoses`): `Pose.Remake` (bool). Write an optional 4th
   segment, `id:item@x,y,z@q@p`, only when true. Parse 3 or 4 segments; an
   unknown 4th segment keeps the pose with `Remake` false. A plugin of
   v0.24.354-356 skips 4-segment entries (`seg.Length != 3`), so after a
   downgrade a re-creatable copy is not moved back. That is acceptable: say
   so in the doc.
3. **Remap** (static in PickupKeeper): `Dictionary<int,int> RemadeFrom` (the
   new copy's instance id -> the captured id) and
   `Dictionary<int,GameObject> RemadeAs` (captured id -> the copy). One helper,
   `CapturedId(GameObject g)`: `RemadeFrom` hit, else `g.GetInstanceID()`. In
   MirrorRoots, when an id is not in `poses` directly, use it:
   - in the TakenList forget-loop: do not forget a target whose `CapturedId`
     is in `poses`;
   - in the re-key loop and in the walk's `poses.TryGetValue`: look up by the
     direct id first, then by `CapturedId`. A re-made copy is then put back /
     kept like the original, never removed as "made since".
   Prune entries whose GameObject is null (a Full load) at the start of each
   MirrorRoots.
4. **Re-make**: during the walk, collect the set of captured ids present (every
   root, active or not, through `CapturedId`, plus TakenList targets). After
   the walk, for each pose with `Remake`, `id < 0`, `Item > 0` and not
   present, do this:
   `Object.Instantiate(prefab.gameObject, pos, rot)`, then zero
   `velocity` / `angularVelocity` on its Rigidbody, `Sleep()`, and record it
   in the remap. Count it by item. A missing prefab is skipped (no throw). The
   pure choice of which ids to re-make goes in `src/Data` with tests, e.g.
   `DroppedPoses.ToRemake(poses, presentIds)`.
5. **Done line**: `, re-made N copy(ies) gone since the capture (Stick x1,
   Rock x1)` (`MirrorResult.Remade` + `RemadeCounts`). Add it to the
   `deleted + rebuilt + spawned > 0` yield. The prefix is unchanged, so the
   log catalogue does not move.
6. **Docs**: docs/savestates.md, the T-0416 paragraph (*A Quick load also
   mirrors the other scene roots*): one sentence on re-making, and the
   downgrade note.

### Tests

  `Remake` false. An unknown 4th segment keeps the pose. `ToRemake` skips
  positive ids, item 0, present ids and non-flagged ones.
- `SavestateFileTests`: unchanged (the line is opaque there).

## The despawn timer: resume it from the capture (proved live, 2026-10-18)

The contract widened (decisions.md *Mirror essentially everything*): a
re-made copy, and a copy T-0416 puts back after it was taken, despawn again
like the game's own. Their timer continues from where it stood at the
capture. Facts for the build:

**Where it lives (IL, `destroyAfter`, a MonoBehaviour on the copy's root).**
- The fields are `destroyTime` (float; 60 on `Stick_Dynamic` / `Rock_Dynamic`),
  `destroyDistance` (float; 20) and `useUnscaledTime` (bool; false).
- `Start`: with `destroyDistance > 0` it calls `InvokeRepeating("destroyMe",
  destroyTime, 10f)`. Else, with `useUnscaledTime`, it starts the coroutine
  `destroyUnscaledTimeRoutine`. Else it calls `Invoke("destroyMe",
  destroyTime)`.
- `destroyMe`: in the distance case it calls `Object.Destroy(gameObject)` only
  while `(LocalPlayer.Transform.position - transform.position).sqrMagnitude >
  destroyDistance^2`. So it checks at 60 s, then every 10 s.
- `OnDisable` and `OnDestroy` each call `CancelInvoke("destroyMe")`.
- No game code keeps the timer's start or remaining time; ILScan finds no such
  field. The `destroyTime` writes are all on other objects: buildings,
  molotov, arrows. Only `ArrowDamage` and `effigyRangeDetect` also use the
  string `destroyMe`, on their own components. Unity 5.6's MonoBehaviour can
  only start, cancel or test an invoke (`Invoke`, `InvokeRepeating`,
  `CancelInvoke`, `IsInvoking`). It cannot read the time left, so the
  plugin has to record the start itself.

**Why a put-back copy stops despawning.** Taking it hides the root:
`PickupKeeper` sets `_disableInsteadOfDestroy`, and the game deactivates the
root. Deactivating runs `OnDisable`, which cancels the invoke. A Quick load's
`PickupKeeper.Restore` calls `SetActive(true)`, but Unity runs `Start` once per
component lifetime, so nothing re-arms it. Live (`restore t418c`): the rock
was active again, `IsInvoking destroyMe` False. With the player 30 m off and
more than 60 s past its drop, it still stood 12 s later.

**Setting it resumes the despawn (live, the player 30 m off):**
- **Re-armed copy:** a fresh stick (`FakeDrop 57`, 5 s old). `CancelInvoke
  destroyMe`, then `InvokeRepeating destroyMe 5 10`: still there at +3 s, gone
  by +7 s. The rock dropped with it, the control, was untouched and still
  there.
- **Put-back copy:** the rock above (no timer). The same two calls: still
  there at +3 s, gone by +7 s.
- **Scaled time:** a rock with `timeScale` 0.25 and `InvokeRepeating destroyMe
  4 10`: still there at 9 s real (2.25 s game), gone by 21 s real. So the age
  is `Time.time` (scaled), as `Invoke` counts it; a pause (timeScale 0) stops
  both.
- **`Start` has run by the next frame:** a copy from `Instantiate` already had
  `IsInvoking destroyMe` True when it was next listed. Re-arm only after
  `Start` ran. Re-arming in the same frame as the Instantiate would leave
  `Start`'s own 60 s schedule as a second one.

**What to capture per copy, and how to resume (build plan).**
1. **Record each start** (src/Game): a Harmony postfix on the private
   `destroyAfter.Start`, installed at plugin start (not only while armed;
   otherwise copies dropped before the first capture have no age). It stores
   `Time.time` by the component's instance id. Store only for a root
   (`transform.parent == null`) with `useUnscaledTime` false; the effects are
   children or short-lived. Prune entries whose component is gone, during the
   capture walk.
2. **Capture** (`CaptureDropped`): for a recorded root with a `destroyAfter`
   that `IsInvoking("destroyMe")`, write the age `Time.time - start` as a
   tag in the optional 4th segment. Make that segment a comma list of tags:
   `p` (re-creatable, from step 1 of the fix) and `t<age>` (invariant
   culture), e.g. `-125484:57@x,y,z@q@p,t37.25`. Parse it tolerantly:
   unknown tags are ignored. A copy with no timer running at the capture gets
   no `t`.
3. **Pure** (src/Data, tests): `DespawnTimer.NextCheck(age, destroyTime,
   repeating)`. Repeating: `age < destroyTime ? destroyTime - age : 10 -
   ((age - destroyTime) % 10)`. Once: `max(0, destroyTime - age)`.
4. **Restore**: in the step after the load, where `_keeper.Restore(present)`
   runs and so after `SetActive(true)` and after a re-made copy's `Start`,
   handle each re-made copy and each put-back copy whose pose has a `t`:
   - `CancelInvoke("destroyMe")`;
   - then `InvokeRepeating("destroyMe", NextCheck(...), 10f)` (or `Invoke`
     when `destroyDistance <= 0`);
   - set its recorded start to `Time.time - age`, so a later capture reads the
     right age.

   Without a `t` (an old file, or none running at the capture), call
   `CancelInvoke` only. That matches the capture. For the re-made copy,
   though, it means "never despawns". If that reads wrong, leave `Start`'s
   fresh 60 s instead (forest-dev picks one, and says so in docs/savestates.md).
   `MonoBehaviour.CancelInvoke(string)` / `InvokeRepeating(string, float,
   float)` / `Invoke` are public Unity calls. Call them on the `destroyAfter`
   component, which is found by its game type name in src/Game.
5. **Tests**: `NextCheck` (before the first check, on the boundary, a later
   repeat); the tags round-trip; `t` without `p` and `p` without `t`.

## Live check (forest-tester, after the release)

Slot 1, uploads off (`_modules[16]._enabled.Value false`), `T =
static:TheForest.Utils.LocalPlayer`, `tp 428 78 -4`.
1. `call $T Inventory.FakeDrop 57 null`, `call $T Inventory.FakeDrop 53 null`,
   `wait 3`, `find _Dynamic 30`: note both positions. `capture t418`.
2. `tp 460 78 -4`, wait about 75 s, then `find _Dynamic 60` shows 0 (the
   game's despawn). `tp 428 78 -4`, `restore t418`. The done line has

   `find _Dynamic 30` shows both within 0.1 m of the noted positions.

   handles still there.

   is back (`pickups put back 1`), with no re-made and no removed.
5. Timer resumed: drop a rock, `wait 20`, `capture t418t`, collect it,
   `wait 5`, `restore t418t`. `call <its root> destroyAfter.IsInvoking
   destroyMe` is True. `tp 460 78 -4`: it is still there about 35 s later and
   gone within 50 s of the restore (60 - 20 = 40 s left at the capture). A
   re-made copy, captured at 20 s old and despawned since, is likewise gone
   about 40 s after the restore.
6. Delete `t418.fosave` / `t418t.fosave`, put uploads back on, close the game.
