# T-0385 Input overlay: a minimal mouse box that keeps the mouse movement informative

Running notes across sessions (docs/harness.md 11a).

- 2026-10-16: forest-ux design research (no code, no game, no pick - the author chooses before any build). Mock-up of all options: `tasks/notes/T-0385-options.svg` (still / slow drift / flick / arc, one row per option).

## What the box is today (code, v0.24.324)

- `InputOverlayModule.SampleMouse` reads the per-frame raw delta (`Mouse X/Y`, or the game's own Mouse X/Y action in game input, so a replay's look shows). It adds `delta * 0.02` to a point (`_mx`, `_my`) that **wraps at +-1**; a trail point every 0.08 of travel, 48 max, fading over 0.6 s (`TrailSeconds`), drawn as GL quads (gotchas 114), split at the box edge (`TrailClip`, T-0380).
- The tile is 2 x 2 units = 92 x 92 virtual px at scale 1 (`InputLayout.BaseUnitsW/UnitsH`), the same height as two key rows; the default block puts it under M1 / M2.
- Only while pressed (T-0383, v0.24.324): drawn only on frames with a non-zero raw delta, trail cut on every still frame. In game that blinks and never builds a path (tester evidence on T-0383); the author's question there (frame-true vs a hold-off) is still parked.
- What the box tells a viewer: the head's **position is the accumulated movement modulo the box**, so it drifts to wherever and means nothing absolute. The informative parts are direction, speed and shape of the last 0.6 s. Everything below keeps those and drops the frame / the meaningless absolute position.

## Research: how other overlays show the mouse

Verified from the pages I could read (univrsal/input-overlay wiki *Usage*): OBS Input Overlay (univrsal) has a **Mouse movement** element with two types: *Moving texture* (a dot that stays at its place and shifts with the mouse up to a "Radius", i.e. an analogue-stick puck) and *Arrow* (rotates around its centre to point where the mouse moves; no radius). Its wheel is a sprite with pressed / up / down states. That is the closest direct precedent: it shows **direction** (arrow) or **deflection** (puck), not a long trail, and both are one small sprite. girlglock/input-overlay (the model of T-0302) lists mouse tracking via RawInputBuffer but its README does not say how the mouse is drawn; I could not read its drawing code, so I do not claim how it looks.
From general knowledge, not fetched here (treat as unverified): game cursor trails (osu!) are a fading comet behind the head; TAS input displays (analog-stick circle with a dot) are the puck.

## Facts the options rest on

1. Direction + speed of the last moment is the useful signal; absolute position is noise (wrap).
2. A real mouse reports on some frames only (T-0383 tester evidence): any option needs a smoothed signal, not the raw per-frame delta, or it blinks. The same smoothed value gives Only while pressed a natural "gone shortly after the last move" instead of a hand-picked hold-off constant. Decision for the author: is a ~0.25 s decay acceptable for the mouse (keys stay frame-true)? It is the open T-0383 question, option (b), done continuously.
3. Per-frame cost stays the same: no allocation, the GL `Quad()` already draws rotated segments (an arrow is 3 quads); `Flat()` draws squares. No rotated GUI textures (gotchas 114).
4. A new look is a runner-facing choice: replace the box or add a style setting (a new word) - not decided here.

## Options

### A - Needle: a 1x1 tile with one arrow (direction + speed)

```
 still        slow            flick           turning
 (hidden)    +----+           +----+          +----+
             | -> |  dim      | \  |  long    | \  |  rotates
             +----+           +----+  bright  +----+  with the mouse
```
- Arrow points where the mouse is moving (smoothed velocity); length and brightness = speed. Fades out ~0.25 s after the last move, so in Only while pressed it simply is not there when still.
- Speedrunner trade-offs: reads a flick's direction and strength at a glance, even on a stream at 480p; half the footprint of today (44 px, beside M1 / M2 instead of under them); no history, so the *shape* of a turn is not shown, only where it points now. Direction is read as an angle, which is quick.
- Fit: smallest change to the box's job: same sampling, replace `DrawMouseBox`; `Mouse` tile becomes 1x1 (saved layouts keep x, y, scale; the tile shrinks to the top-left of where it was). The univrsal "Arrow" precedent.

### B - Comet: no frame, the head fixed, a tail of the last 0.4 s

```
 still     slow         flick           turning
  .       ---.             .             /\
                            \           /  .
                             \         .
```
- No border, no fill: just the dot and its fading path, drawn **relative to the head** (the head stays put and the path is the motion that led to it), so there is no wrap, no edge split and no drift. Fades to nothing by itself, so Only while pressed needs no extra rule, and because the tail persists for ~0.4 s the blink goes (the path keeps building across frames the mouse did not report).
- Speedrunner trade-offs: the only option that shows the *shape* (arc, zig-zag, a straight flick) - useful to see a precise camera route; smallest footprint when idle (nothing); but floating lines on top of the game with no anchor can be lost on a bright snow or sky background, and it is the busiest to read at stream quality. A faint 1 px ring could anchor it (extra choice).
- Fit: reuses the trail code (ring buffer, GL quads, fade). Drop the box draw and `TrailClip` split (path stored relative, no wrap). Tile size becomes just the path's room (about 1x1 or 1.5x1.5); the tile is invisible so Edit HUD still needs an outline to place it (it already draws one).

### C - Puck: a 1x1 tile with a dot pushed off centre (deflection, springs back)

```
 still      slow        flick (pinned)   turning
 +---+     +---+        +---+            +---+
 | + |     | +.|        |.  |            | .+|   circles the centre
 +---+     +---+        +---+            +---+
```
- Dot offset = smoothed velocity, clamped to the tile; returns to the centre when the mouse stops (hidden there in Only while pressed). The univrsal "Moving texture" and the TAS stick display.
- Speedrunner trade-offs: familiar to anyone who has seen a TAS stick display, and an X / Y read (is it left or up) with a visible magnitude; but the dot is clamped at the rim for any fast flick, so a flick and a hard flick look the same unless the rim has a scale; and the position, not an angle, takes a moment longer to read than an arrow.
- Fit: the cheapest change from today (the same tile, a dot; no GL, no trail), keeps the tile frame (consistent with the key tiles' look), 1x1 or keep 2x2 for finer resolution.

## Recommendation (design view only; the author picks)

Needle (A) answers "what direction and how hard" at the smallest size and has a real precedent; Comet (B) is the only one that keeps the *shape* and solves the blink with no new constant, at the price of readability on a bright scene. A and B can coexist as a "Mouse style" setting at the cost of a new runner-facing word. Whichever is picked, the smoothed velocity and its decay time is the one new constant the author must accept, and it replaces the blink question in T-0383.

Questions for the author (not filed - this task was told not to file): which of A / B / C (or a setting for two of them); the mouse's decay time in Only while pressed (a fixed ~0.25 s vs frame-true and blinking); a 1x1 tile replacing the 2x2 box (saved layouts keep their x / y / scale) or a new tile kept next to it.
