# T-0382: the frozen game and the blank monitor (2026-10-15 22:59 UTC)

Offline research only (author's answer, 2026-10-16): Windows event log,
the tester's transcript, the bridge folder, unity.log / stall.log, the
bridge resize + screenshot code, the GL build. No live repro.

## Cause

**The NVIDIA driver faulted (System log `nvlddmkm` Event 153, "Error
occurred on GPUID: 100", 7 events at 22:59:17.243-.248 UTC, one more at
22:59:19.149)**. The resize did not cause it, and neither did the screenshot.
After the fault every `Application.CaptureScreenshot` failed, and the game's
main loop kept running. The monitor most likely lost its signal at the same
moment (the timing fits). Logs cannot prove that: Windows logs no
display-link event. The PC is an RTX 4080 SUPER on driver 617.42.

Whether the GPU fault is hardware, driver or overclock, the logs cannot
settle it. That question is for the author (see Decisions).

## The fix (tooling, not the plugin)

There is nothing to change in the plugin or the resize recipe. What went
wrong for the tester was that nothing told it the GPU had faulted. It
retried screenshots three times, and the author found a blank screen.
Make the bridge MCP say so:

1. **New pure file `tools/BridgeMcp/GpuFaults.cs`**, linked into
   `tests/ForestOverlay.Tests` the way `LogSearch.cs` is:
   - `Parse(string eventXml)` turns `wevtutil qe System /f:xml` output
     into a list of (UTC time, provider, event id, first message string).
   - `Summary(list, sinceUtc)` returns `null` when the list is empty, else
     one line: `GPU driver fault: <n> event(s) since the game started,
     first <hh:mm:ss> UTC (<provider> <id>: <text>) - the display may be
     blank and screenshots fail; stop driving the game and tell the
     author`.
   - The providers to read: `nvlddmkm`, `amdkmdag`, `amdwddmg`, `igfx`,
     `igfxn`, plus `Display` event 4101 (the Windows "display driver
     stopped responding" event).
2. **Reading the log**: either `wevtutil qe System
   /q:*[System[Provider[@Name=...] and TimeCreated[@SystemTime>='<game
   start, UTC, ISO>']]] /f:xml /c:50` through `ChildProcess` (stdin
   closed, gotcha 95), or `System.Diagnostics.Eventing.Reader.EventLogReader`
   (the System.Diagnostics.EventLog package; Windows only, which the MCP
   already is). An unprivileged user can read the System log (this
   research read it). Any failure means no line, never an error.
3. **`status`**: append the summary (or nothing) after the `game: running`
   line, with the process `StartTime` as `since`.
4. **`screenshot`**: when `Images.ReadWhenComplete` throws "never appeared
   complete", check `GpuFaults` since the game started and put the summary
   into the error text.
5. **docs**: `.claude/agents/forest-tester.md` (and the bridge-test skill
   step on screenshots) gets one rule. A screenshot that never appears
   means run `status`, and if it names a GPU fault, stop: no retries, no
   more resizes; report it. Whether to close the game is the author's call
   (Decisions).

Tests (`tests/ForestOverlay.Tests/GpuFaultsTests.cs`):
- Parse a trimmed real payload. The 22:59:17 `nvlddmkm` 153 event with
  `<Data>\Device\000000f0</Data><Data>Error occurred on GPUID: 100</Data>`
  and a `Reset TDR occurred` one give the right time, provider, id and text.
- Summary is null for no events, and for events only before `since`.
- Summary counts, and names the first event's time and text.
- Garbage or empty XML gives an empty list, no throw.
