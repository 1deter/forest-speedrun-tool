# T-0382: the frozen game and the blank monitor (2026-10-15 22:59 UTC)

Offline research only (author's answer, 2026-10-16): Windows event log,
the tester's transcript, the bridge folder, unity.log / stall.log, the
bridge resize + screenshot code, the GL build. **Nothing here is confirmed
live.** The repro plan below is for when the author is present.

## Leading hypothesis (not confirmed)

At 22:59:17.243-.248 UTC the System log records 7 `nvlddmkm` Event 153
entries ("Error occurred on GPUID: 100"), plus one more at 22:59:19.149.
These are NVIDIA driver errors. That moment matches the first screenshot
that never appeared. From then on every `Application.CaptureScreenshot`
failed, while the game's main loop kept running. **The leading hypothesis:
a GPU driver fault froze the picture, and probably took the DisplayPort
signal with it.** Windows logs no display-link event, so the signal loss
is inferred from the timing alone. What triggered the fault is open (the
ranked list below). The PC is an RTX 4080 SUPER on driver 617.42.

## Candidate causes, ranked

1. **A driver / GPU fault on its own** (hardware, driver or clock
   instability, with the game as just the load at that moment).
   - For: faults from July on, many before the plugin existed or with no
     agent driving (evidence 3). All three in-test faults share the same
     generic payload, on different builds. The 04:15 TDR came on a build
     without the GL path and with no resize near it.
   - Against: this one landed inside a test, within 3 s of a new draw path
     starting. A load-sensitive fault would look exactly like that, so the
     history cannot separate "on its own" from "triggered".
2. **The GL mouse path, under the `mouse_event` circles from 22:59:14.6**
   (about 2.6 s before the fault).
   - For: it is new GPU work in this build (diff below). It ran at the
     moment of the fault. The 64c8e922 version drew nothing visible
     (gotcha 114: wrong space), so its quads went somewhere unintended.
     That is still valid API use, but nothing proves the driver handled
     it well. Earlier faults on non-GL builds do not rule it out.
   - Against: in this deployed build the same path ran under `mm.py`
     circles about 12 times, for 4-8 s each (22:55:26 to 22:59:02, both
     resolutions, roughly 75 s in all), with no fault. What was new in
     the faulting run: the mouse tile at scale 2 (thicker quads, a bigger
     box, set at 22:59:00), amplitude 12 instead of 30, and the tile moved
     to Y 300. One fault in about 80 s of GL time is too little to call it.
3. **A long-running GPU** (heat or clocks after hours of tests).
   - For: the faults cluster in long sessions (08-28 19:23-22:10, 09-02/03,
     this evening from 22:33 on).
   - Against: this game process was 1.5 min old. No temperature or clock
     data exists for 22:59. The 04:15 and 10-16 08:26 TDRs fit any of the
     four candidates.
4. **The 2560x1440 switches** (a window the monitor's full size, then back
   to 1920x1200).
   - For: two round trips came in the 2.5 min before the fault. The 10-11
     fault came 19 min after 2560x1440 calls.
   - Against: 17 s and one good capture came between the last resize and
     the fault. 24 other resize calls, the same switches on v0.24.310
     included, were not followed by a fault, and the 04:15 TDR had no
     resize near it. A windowed `SetResolution` is expected to resize the
     window and swap chain without a display-mode change (not verified).
5. (Minor) **The label size change at scale 2**: the W tile's font went to
   26 px at 22:59:00, a dynamic-font atlas rebuild (a texture upload).
   - For: it is GPU work new in this build.
   - Against: it was a one-off 17 s before the fault.

## What the GL build changed against v0.24.310 (the GPU-touching parts)

Diff v0.24.310 -> 64c8e922 (`src/Modules/InputOverlayModule.cs` +141/-23;
`UiKit.cs` adds two colour getters; `Plugin.cs` the version). All drawing
happens on Repaint only.

- **New: an immediate-mode GL batch per frame.** `EnsureLineMaterial`
  makes one `Material(Shader.Find("Hidden/Internal-Colored"))` (blend
  SrcAlpha / OneMinusSrcAlpha, cull off, ZWrite 0, ZTest Always). Then
  `DrawMouseBox` runs, while the trail has points (`_trailCount > 0`;
  it stays at 48 while the mouse moves):
  `GL.PushMatrix(); GL.MultMatrix(GUI.matrix); _lineMat.SetPass(0);
  GL.Begin(GL.QUADS)`, then up to 47 quads (4 vertices with per-vertex
  colour each), then `GL.End(); GL.PopMatrix()`. This runs inside
  OnGUI, between IMGUI draws. In v0.24.310 the trail was IMGUI
  `WinPx.Box` squares (style `UiKit.Handle`).
- **Changed: tile frames, the lit fill and the dot.** They now use
  `WinPx.DrawTexture(Texture2D.whiteTexture)` with `GUI.color` instead of
  styled `WinPx.Box` (9-slice textures). That is the same IMGUI quad path,
  with a different texture.
- **Changed: label font sizes.** One style per state, with `fontSize` set
  per tile to `round(13 * scale)` (min 6), instead of three fixed sizes
  (13 / 18 / 26). Mixed tile scales flip one style's font size within a
  frame, and new sizes add glyphs to the dynamic font atlas (texture
  rebuilds). `CrispText.Label` itself did not change.
- Nothing else in the diff touches rendering (snap / inset helpers are
  arithmetic).

## The tooling fix (independent of the trigger)

Whatever the trigger, the tester went on to retry screenshots three times
with no idea the GPU had faulted. Make the bridge MCP say so:

1. **New pure file `tools/BridgeMcp/GpuFaults.cs`**, linked into
   `tests/ForestOverlay.Tests` the way `LogSearch.cs` is:
   - `Parse(string eventXml)` reads `wevtutil qe System /f:xml` output
     into a list of (UTC time, provider, event id, first message string).
   - `Summary(list, sinceUtc)` returns `null` when nothing is at or after
     `sinceUtc`. Otherwise it returns one line: `GPU driver fault: <n>
     event(s) since the game started, first <hh:mm:ss> UTC (<provider>
     <id>: <text>) - the display may be blank and screenshots fail; stop
     driving the game and tell the author`.
   - Providers: `nvlddmkm`, `amdkmdag`, `amdwddmg`, `igfx`, `igfxn`, and
     `Display` event 4101 (the Windows "display driver stopped
     responding" event).
2. **Reading the log**: either `wevtutil qe System /q:<xpath: those
   providers, TimeCreated >= game start UTC> /f:xml /c:50` through
   `ChildProcess` (stdin closed, gotcha 95), or `EventLogReader`
   (System.Diagnostics.EventLog package, Windows only, like the MCP). An
   unprivileged user can read the System log (this research did). Any
   failure means no line, never an error.
3. **`status`**: after the `game: running` line, append the summary
   (`since` = process `StartTime`).
4. **`screenshot`**: when `Images.ReadWhenComplete` throws "never appeared
   complete", put the summary into the error text.
5. **forest-tester rule** (`.claude/agents/forest-tester.md` and the
   bridge-test skill): when a screenshot never appears, run `status`. If
   it names a GPU fault, stop: no retries, no more resizes. Report it.

Tests (`tests/ForestOverlay.Tests/GpuFaultsTests.cs`):
- A trimmed real payload parses. The 22:59:17 nvlddmkm 153 event
  (`<Data>\Device\000000f0</Data><Data>Error occurred on GPUID:
  100</Data>`) and a "Reset TDR occurred" event give the right time,
  provider, id and text.
- Summary is null with no events, and with events only before `since`.
- Summary counts the events and names the first one's time and text.
- Garbage or empty XML gives an empty list, without throwing.

**MCP-line check** (forest-tester, after the MCP rebuild; no fault needed):
1. Run `status` with the game running. It shows no "GPU driver fault"
   line, unless `wevtutil qe System
   /q:"*[System[Provider[@Name='nvlddmkm'] and
   TimeCreated[@SystemTime>='<launch UTC>']]]" /c:5` lists events; then
   the line must show them.
2. A normal `screenshot` still returns the image.
3. The fault text itself is proven by the unit test on the real payload.
   Never provoke a fault for it.

## Live repro plan (only with the author at the PC)

Goal: find which candidate triggers the fault, or that none does. A
fault came once in about 80 s of GL time, so a phase without a fault
proves little. Each phase gets a fixed time budget, and the rate is what
gets compared.

**Before**
- Back up Slot 1 (`Slot1.deter-backup`) and turn uploads off
  (bridge-test skill).
- Say in chat and with `notice` that the screen may go blank.
- Baseline the log: `wevtutil qe System
  /q:"*[System[Provider[@Name='nvlddmkm']]]" /c:3 /rd:true /f:text`.
  Note the newest event's time.
- In the background, log the GPU once a second to the scratchpad:
  `nvidia-smi --query-gpu=timestamp,temperature.gpu,clocks.gr,clocks.mem,power.draw,utilization.gpu --format=csv -l 1 > gpu.csv`.
- The mouse driver, as the tester ran it, saved to the scratchpad as
  `mm.py`: `import ctypes,math,time,sys; u=ctypes.windll.user32;
  dur=float(sys.argv[1]); amp=float(sys.argv[2]); t0=time.time(); a=0`,
  then loop while `time.time()-t0<dur`: `a+=0.1;
  u.mouse_event(1,int(round(amp*math.cos(a))),int(round(amp*math.sin(a))),0,0);
  time.sleep(0.016)`. It is bounded by `dur`. Foreground the game first
  (`scripts/sendinput.py` does it; gotcha 115).

**After every step, watch**
- New nvlddmkm events (the query above).
- `Failed to capture` in unity.log / `log`.
- `status` (frames advancing).
- The author's eyes on the screen.

**Stop rule**: at the first new event, failed capture or blank screen, stop
sending commands. Let `mm.py` end, or kill it (`ps -ef | grep mm.py`,
`kill`). Note the times. The author chooses: `game close`, or leave it to
look at. No retries.

**Phase A: the exact replay** (build 64c8e922: a worktree at that commit,
build, `scripts/deploy.ps1`, game closed first)
1. Launch, load Slot 1, `tp 428 78 -4`, Inputs on.
2. `SetResolution 1920 1200 false`, `wait 3`; `mm.py 6 30` and a shot.
3. `SetResolution 2560 1440 false`, `wait 3`; `mm.py 6 30` and a shot.
4. `game restart`, load Slot 1, `tp`, Inputs on, then steps 2-3 again.
5. `SetResolution 1920 1200 false`, then Tiles[9].Y 300, Tiles[9].Scale
   2, Tiles[0].Scale 2; `wait 3`; `mm.py 6 30` and a shot.
6. `mm.py 6 12` with `screenshot delay_s 2.5`, repeated for 5 min.

**Phase B: split the candidates** (5 min each, in this order; at a fault,
apply the stop rule, then go on only if the author wants)
- B1, GL without resizes: build 64c8e922, 1920x1200 from launch, no
  `SetResolution`, Tiles[9].Scale 2, `mm.py 6 12` back to back.
- B2, the same without GL: v0.24.310 (its path is IMGUI squares), the
  same steps as B1.
- B3, resizes only: Inputs off, the mouse still, 20 round trips of
  `SetResolution 1920 1200 false` / `wait 3` / `SetResolution 2560 1440
  false` / `wait 3`, with a shot after each.
- B4, idle load: the game at the spot, nothing driven, 5 min.

**Reading it**: compare the fault rate per phase.
- A fault in A / B1 but not in B2-B4 points at the GL path (candidate 2).
- A fault in B3 only points at the resizes (candidate 4).
- Faults in B4 or scattered across phases point at the driver / GPU
  (candidate 1), with gpu.csv for heat or clocks (candidate 3).
- No fault anywhere settles nothing. Record it and close the repro.
