## Build plan (forest-researcher, 2026-10-21; for forest-dev)

Evidence for every row: docs/run-mode.md *Red team* (log / report lines
quoted there, all on v0.24.397, test attempts deleted). No fix needs
live tuning: each threshold below is a vanilla value read live. The
stand-in cheat mod is `tools/RedTeamProbe` (build: see its csproj).

Shared rule: every new check is read-only, flags through `Ctx.Run.Flag`
during an open attempt, is skipped while `excused` (RunModeModule.Tick:
not loaded, a savestate action, a cutscene fast-forward), and its pure
part lives in `src/Data` with tests. No allocation per frame (the reads
are FastField / Unity statics; texts built only when a flag fires).

**F1 - the game clock ran faster than real time** (covers the
`timeScale` flip-flop and `captureFramerate`). Live fact: `deltaTime /
unscaledDeltaTime` is never above 1.0000 in vanilla (play, Full load,
pause menu, inventory); a `timeScale` 2 written in `LateUpdate` and put
back to 1 at the start of `Update` gave ratio 2 on 873 of 949 frames with
`timeScale` reading 1. Build `ClockWatch` in `Data/SpeedCheck.cs`, shaped
like `TimeScaleWatch` (episode: flag on the first frame, an end line with
the peak and the unscaled seconds): irregular when `unscaledDt > 0` and
`dt > unscaledDt * 1.01`. Feed it in `RunModeModule.Tick` beside the
time-scale watch with `Time.deltaTime`, `Time.unscaledDeltaTime`, and only
when `Time.timeScale <= 1` (a plain `timeScale` 2 stays the time-scale
watch's one flag, not two). Flag text e.g. "the game's clock ran faster
than real time (x2, time scale read 1)"; end line "game clock x2 lasted
5.0 s (back to real time)". Tests: vanilla frames (1, 0, 0.1-load frames
with ud large) silent; ratio 2 flags once per episode, end line; excused
frames start nothing; ratio 1.005 silent.

**F2 - `Time.captureFramerate`** (no writer in any game assembly; our TAS
stops when run mode starts, TasModule line ~422). Any value but 0 during
an attempt: flag once per attempt "the game's clock was locked to N
frames a second (capture frame rate)". Text helper + test in SpeedCheck.

**F3 - movement constants** (live, Normal and Creative alike; IL: no
writer raises them). Extend `Game/SpeedRead` with `walkSpeed`,
`strafeSpeed`, `crouchSpeed`, `jumpHeight`, `gravity` (FirstPersonCharacter
floats, FastField), read `Physics.gravity` and `Time.fixedDeltaTime`
directly. Pure `SpeedCheck.MovementFlag(...)` -> null or one text naming
every value off: walk > 6.5, strafe > 6, crouch != 4.5, jump != 8,
gravity != 10 (each +- 0.01), Physics.gravity != (0, -16, 0) (+- 0.01 a
component), fixedDeltaTime not within 1e-5 of 1/60 or 1/30 (skipped when
`RunIntegrity.IsMultiplayer()`: Bolt sets 1/its fps). Once per attempt,
its own `_moveFlagged` (separate from `_runSpeedFlagged`), same place in
Tick. Tests: vanilla silent, the lowered hit-reaction values (1.2, 0, 1)
silent, each raised value named, 1/30 silent (until D1), 1/120 named.
`maximumVelocity` is not watched (the game rewrites it every frame).

**F4 - the start state a run spot really loaded.** `SavestateModule
.RestoreStartState` already computes `Segment.HashText(f.Data)` (the
warning at ~line 2540): keep it in a public `LastStartStateHash` (set for
every read, "" on failure). `RunModeModule.SpotRunReady`: use that hash in
`started` ("start state <loaded>") and in the chain header
(`RunModeModule.Codes` line ~106, now `_runSpot.StartState`); when the
spot names a hash and it differs, after `StartAttempt` flag "the run
spot's start state is not the one the spot names (loaded X, the spot
names Y)". Pure text helper + test. Live proof of the gap: a spot with
`startstate = 12345678` started an attempt reporting "start state
12345678" with only the log warning.

**F5 - patch ownership by assembly, not by id prefix.**
`RunIntegrity.SortPatches`: a patch is ours only when the owner starts
with our GUID **and** the patch method's declaring assembly is ours
(`typeof(RunIntegrity).Assembly`); otherwise it is listed, as
"Type.Method (by <owner>, from <assembly name>)" when the owner borrows
our prefix. Put the decision in `Data/PlatformPatches` (e.g.
`IsOurs(owner, ownGuid, patchAssembly, ownAssembly)`), tests incl. the
`com.deter.forestoverlay.cheat` case. Live: every one of our patches has
its method in ForestOverlay; the borrowed-prefix patch was not listed.

**F6 - detours that are not Harmony's.** MonoMod keeps every detour in
`MonoMod.RuntimeDetour.Detour._DetourMap` (static, non-public;
`IDictionary` MethodBase -> List of Detour; each Detour's `Target` field
is the replacement). Harmony makes one detour per patched method. In
`RunIntegrity.GatherPatches`, by reflection (null-safe: a BepInEx without
the field just skips): list a map key that `Harmony.GetAllPatchedMethods`
does not hold, and a Harmony-patched key with more than one detour, as
"Type.Method (a detour, not Harmony: <target's assembly or 'code with no
file'>)", skipping BepInEx / Harmony's own three (live baseline: key
`ILHook+Context.Refresh` and `StackFrame.GetMethod` with a target in
`0Harmony`; key `HarmonyInteropFix.LoadFile`, declared in
`BepInEx.Preloader`). The skip rule pure in `Data/PlatformPatches`
(`IsPlatformDetour(keyAssembly, targetAssembly)`), tested. Change
detection: add the map's `Count` to what `RunModeModule.Watch` and
`ExternalModWatch.Tick` compare (beside `PatchedCount`). Live: a MonoMod
`Hook` on `ItemDatabase.ItemIdByName` added a map entry whose target is
`Hook<...>` (dynamic); 122 keys vs 119 Harmony methods with the Hook on
a Harmony-patched method = the hook sat in that key's list.

**F7 - code loaded from memory.** `RunIntegrity.GatherMods` skips an
assembly with an empty `Location`: list a non-`AssemblyBuilder` one with
no file as "<name> (loaded from memory)", except the known four (live
baseline, both launches): `Rewired_Windows`, `Rewired_Config_Manager`,
`Rewired_Config_ManagerA`, `MonoMod.Utils.GetManagedSizeHelper`. Known
list + check pure in `Data/ExternalMods`, tested. `ExternalModWatch`
already re-gathers on every `AssemblyLoad`, so a mid-run injection
reaches the session flag and the attempt's "Mods Detected" by itself.

**F8 - files in the trusted folders.** `GatherMods` trusts any assembly
under `TheForest_Data/Managed` and `BepInEx/core`: trust only the file
names a clean install has there (Managed: the 49 `*.dll` of the author's
install, `ls` it; core: `0Harmony`, `0Harmony20`, `BepInEx`,
`BepInEx.Harmony`, `BepInEx.Preloader`, `HarmonyXInterop`, `Mono.Cecil`
(+ `.Mdb`, `.Pdb`, `.Rocks`), `MonoMod.RuntimeDetour`, `MonoMod.Utils`);
any other file there is "other code". Lists in `Data/ExternalMods`,
tested. Live: `RedTeamExtra.dll` loaded from Managed was not listed. (A
game or BepInEx update that adds a file shows as other code until the
list follows - /admin/allowed covers it meanwhile.)

**F9 - our patcher by path, not by name.** `GatherMods` skips any
`ForestOverlay.Updater.dll` under `BepInEx/patchers` (subfolders too) and
any loaded file of that name: skip only
`<patchers>/ForestOverlay.Updater.dll` itself (compare normalised full
paths). Live: `patchers/redteam/ForestOverlay.Updater.dll` was not
listed while `patchers/RedTeamPatcher.dll` was.

Docs with the build: run-mode.md *Red team* rows -> "yes (F-n)", the
*Banned moves* table's speed rows, log-lines.md for any new prefix
(the flags reuse "Run mode:"), quality.md's Run mode row.

### Decisions for the author

- D1: `fixedDeltaTime` 1/30 is the game's hidden *Low quality physics*
  option (`PlayerPreferences.LowQualityPhysics`, the console's
  `physics30Fps`) and changes movement tech - allowed, a note, or a flag?
  (F3 leaves it silent until decided.)
- D2: own run spots: the site does not compare an attempt's spot / start
  state with the category's `spot =` - should another spot be amber or
  red for a category that names one?
- D3: *Start run mode* by hand after practice in the same session gives
  only a note - a savestate restored just before lets a run start at any
  point. Amber, a flag, or keep it a note?
- D4: the start-state hash is 32-bit FNV-1a over the state's text, so a
  state can be forged to match; SHA-256 would stop that but changes
  every spot's route fingerprint.
- D5: bridge `tp` is not refused in a run (the attempt is flagged by the
  bridge anyway) - refuse it like `go`?
