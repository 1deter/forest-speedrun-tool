## What was proved live (test build, Slot 1, 2026-10-16)

A throwaway `ArmsReplicaTest` MonoBehaviour (not committed) sampled the
live animator every LateUpdate and played it back 0.3-1 s late on an
`ArmsReplica`, placed 3 m in front of the player or 30 m to the side with a
picture-in-picture camera on the copy's head:

- Build: 12.5-16.9 ms once, 276 components stripped, **0 left, no Unity
  errors** (after the dependency-aware strip), 334 renderers, 16 in-body
  held models mapped. `LocalPlayer.Animator / AnimControl / ScriptSetup /
  MainCam / CamFollowHead` and the held models stayed the live player's.
- Pose: a plane-axe swing (`stickAttack`), a sprint (`axis Vertical` +
  `hold Run`) and looking down / up replayed; head joint error 0.000-0.002 m;
  a camera on the copy's head showed the arms, lighter and axe in the same
  place as the live view (shots `arms-pip-*.png`, `arms-front-*.png` in the
  bridge folder).
- Held: `SetHeld` swapped in the spear (56) and flare (43) - FakeParent'ed
  models copied under the copy's `rightHandHeld` - and hid the lighter.
- Cost: reading 6 layers + 35 floats 2.4 us a frame, no allocation;
  posing (6 Play + 35 SetFloat + Update(0)) 0.19 ms a frame.
- Data rates: layer state changes 2 in 1,551 frames (running, looking), 8
  in 1,006 (with a swing); layer-frames in transition 63 / 263; floats
  changed (> 0.01) in ~30 % of frames (vSpeed, overallSpeed, normCamX lead).

## Build plan (forest-dev) - superseded in its cadence and lines

Built as c8c0edf6 (10 Hz `a|` samples); the checker blocked it and the
rate comparison below replaced the recording and the posing. The rest
(the replica's build, held models, the camera) stands.

### 1. Pure data (`src/Data`, tests)

`Data/AnimTrack.cs` (new), attached to `Attempt` as `Anim` (null = none):
- `string[] Floats` - the float parameter names, recording order.
- `int Layers`.
- Samples in flat lists, no per-sample arrays (verify: no per-frame
  allocation): `List<float> T`, `List<float> Yaw`, `List<int> Hash`,
  `List<float> Time`, `List<float> Weight` (Layers entries per sample;
  layer at weight 0 stored as hash 0, time 0, weight 0).
- `List<AnimFloat>` {T, Index, Value}: only changes (> 0.01 from the last
  written), all on the first sample.
- `List<AnimHeld>` {T, int[] Ids}: the equipment slot ids when they change
  (rare - an array per change is fine).
- `PoseAt(float t, int[] hash, float[] time, float[] weight, float[] floats, out float yaw)`
  into caller buffers: per layer, same hash in the samples around t ->
  lerp time and weight; different -> the earlier sample's state (a
  switch shows at its recorded time). Floats: lerp between the change
  points (step if no later change). `HeldAt(t)`: last change <= t.

`Data/AttemptFormat.cs`, new lines (older readers and the site skip them;
the dispatch compares `p[0]` exactly, so `a` is safe beside `anchor`):
- `anim|<layers>|<float name>|...` - header, once.
- `a|<t>|<yaw>|<hash>:<time>:<weight>|...` - one entry per layer; `-` for
  a layer at weight 0; layer 0 written without weight. Time F3 (Unity's
  cumulative normalizedTime - interpolates without wrapping), weight F2,
  yaw F1 (the player root's yaw: the body may face away from the look).
- `af|<t>|<index>=<value>|...` F3.
- `ah|<t>|<id>|<id>|...`.
- `InsertRunnerLine`'s header-end list (line ~337) gets `anim`, `a|`,
  `af|`, `ah|`.

Tests (`tests/`, pattern of the `l|` look track and `ReplayMarksTests`):
round trip of all four lines; a run without them parses with `Anim ==
null` and replays as today; `-` layers; PoseAt lerp on the same hash,
step on a change, float lerp / step, HeldAt; unknown lines still skipped.

### 2. Recording (`Data/RunRecorder` + `Game/`)

- `RunRecorder.AnimSource` (delegate like `LookSource`): asked on a 10 Hz
  cadence (`AnimInterval = 0.1f`, its own timer like `_nextStateTime`),
  fills reusable buffers; the recorder appends to the flat lists and
  diffs floats / held ids itself. 10 Hz + interpolation: measure the file
  growth per minute (verify) - estimate ~+80 KB/min on ~110 today.
- `Game/AnimReader.cs` (new): `AnimProbe.PlayerAnimator()`; float hashes
  and names cached once from `Animator.parameters` (allocates - once per
  animator instance, re-read when the instance changes after a load);
  per sample: `GetCurrentAnimatorStateInfo(i)` (fullPathHash,
  normalizedTime); if `IsInTransition(i)` and
  `GetAnimatorTransitionInfo(i).normalizedTime >= 0.5` the next state's
  (`GetNextAnimatorStateInfo`); `GetLayerWeight(i)`; `GetFloat(hash)`;
  yaw = `Ctx.Player.Transform` (the recorded position's transform)
  eulerAngles.y. Held ids: `PlayerInventory._equipmentSlotsIds` (int[5])
  through `FastField`, copied into the buffer.
- Unlike `ReadLook`, not skipped while freecam flies the view: the
  animator is the player's either way, so it records while a run runs.

### 3. Playback (`Modules/PracticeRunModule.Camera.cs` / `.Replay`)

- First person with `_reference.Anim != null`: build the replica lazily
  (`ArmsReplica.Build(Ctx.Log, out why)`) **before** `_replayCam.Begin` or
  on the first FirstPerson frame (CamOffset falls back to 0.05 m if the
  camera is already flown); `Prepare(every held id in the track)` right
  after (one hitch, not mid-replay). Build failed -> today's view + a
  status line why.
- Each tick in FirstPerson: `PoseAt(_clock.T)` -> `Place(P, yaw)` (P = the
  position track's point at t, as the ghost) -> `Pose(layer...)` per layer
  -> `SetFloat(Animator.StringToHash(name) cached, v)` -> `SetHeld` when
  HeldAt changes -> `Evaluate()` -> camera at `EyeAt(look rotation)` with
  the recorded yaw / pitch (instead of P + eye). `Show(false)` in chase /
  trajectory; `Destroy()` in `EndReplayCamera`; `!Alive` after a load ->
  rebuild on the next FirstPerson frame.
- Runs tab line: "first person: arms recorded / not recorded (older run)".
- Log lines: `Replay camera: arms ...` once per build / failure (the
  `Arms replica:` line already logs the build).

### Known gaps (say so in the docs, not blockers)

`playerAnimatorControl.LateUpdate`'s bone tweaks are not replayed (neck
pitch 5 deg/unit, torch arm, flintlock aim); the lit lighter shows unlit;
endgame cutscene clips are swapped into the shared override controller
only while the live player is there (`AnimationLoadManager`); layer
crossfades snap at their midpoint.

## Rate comparison: 30 Hz, 10 Hz, changes only (2026-10-16, author's question)

The checker blocked c8c0edf6 (10 Hz chosen by the maker; the contract said
30 Hz). Author: try 30 Hz, 10 Hz and changes only, measure, pick the best
long-term option that does not compromise analysis.

**Method.** A throwaway test build recorded the live animator every frame
(each layer's state, normalized time, length, weight; in a crossfade the
next state, its time and the progress; the 35 floats) together with the
live head joint and the `rightHandHeld` / `leftHandHeld` bones in the
body's space, for 55 s of one bridge script: 9 plane-axe / spear swings
(some looking down), 2 sprints, looks up / down / around, a jump, strafes,
4 item switches (spear, flare, axe). Recorded at 60 fps (3,317 frames) and
uncapped (~186 fps, 10,182 frames), saved to disk, then each scheme was
built from the same frames and replayed onto `ArmsReplica` at every
frame's time; error = distance of each bone from the live one. Sizes are
the scheme's lines as AttemptFormat would write them.

**60 fps** (errors in mm; "crossfade" = frames with a layer mid-transition,
20 % of them; worst bone per frame, mean):

|---|---|---|---|---|---|

| 30 Hz, same method | 207.9 | 12.5 / 22.9 / 15.6 | 76.7 | 14.6 | 702 / 331 |

**186 fps** (10,182 frames): 10 Hz built 75.2 KB/min, 26.5 / 35.9 / 25.8 mm,
crossfade 96.1; 30 Hz built 216.7, 21.3 / 22.6 / 17.4, 60.8; 30 Hz +
crossfade + every float 763.8, 7.2 / 2.7 / 2.0, 10.3; dead reckoning 63.0,

(`playerAnimatorControl`'s neck pitch, not recorded) - the hands show the
real difference. The pure changes-only scheme with per-frame float polling
grew to 178 KB/min there (float noise per frame): floats belong on the
30 Hz tick.

The one 0.75-1.9 m outlier in every row is a single live frame where a
layer switched off for one frame (t = 21.39 s), not a replay error.

**Visible differences** (same moment, camera on the copy's head with the
recorded look; `m-1607.png`, `m-1776.png`, `m-2116.png` in the bridge
folder, each 2 x 2: reference / 10 Hz built / dead reckoning / 30 Hz
built): mid-crossfade at a swing's start (progress 0.66) both built rates
already show the next state - the axe raised and turned - while dead
reckoning is the reference; in the wind-up the built rates hold the fist
higher and closer; in the fast downswing all are close. Shipped replay in
the real Runs tab first person: `replay-5830/5860/5900/7200.png` (wind-up
mid-crossfade, top of the swing, downswing, walking).

**Why dead-reckoned changes only** (chosen, built):
- The rate was not the main lever - the playback method and the floats
  were. 30 Hz with the built method still put the hands 7.7 cm off on
  crossfade frames: `Play` shows one state and snaps halfway through a
  0.1-0.3 s crossfade, and the floats were smeared by interpolating
  between change points.
- 10 Hz cannot follow crossfades (1-3 samples each): 5.6 cm on those
  frames even with the crossfade replayed.
- 30 Hz samples with the crossfade replayed are good (~4 mm) but cost
  230 KB/min - nearly doubling a run file - and a state change still
  lands up to 33 ms late.
- Pure changes only is small but drifts: a blend tree's length changes
  with its floats (walk / run cycle), and a crossfade's progress has no
  readable duration in Unity 5.6, so playback alone runs off (7 cm on
  crossfades).
- Dead reckoning keeps the small size (48-64 KB/min, less than the built
  10 Hz) and is the most accurate (shipped: hands 1.6-2.5 mm mean, the
  worst bone 2.9 mm on crossfade frames at 60 fps); each state change is keyed on the frame it happened, so
  the timing of a swing or an equip is frame-exact for analysis; the
  track holds both states of every crossfade with its progress and rates,
  so the site (T-0281) or a later player can blend or analyse it; the
  thresholds are constants (tighter later needs no format change).
- Cost: reading + keying 2.4 us a frame with **0 bytes** allocated
  (20,000 calls on the live animator, no GC); replay posing 0.24-0.27 ms a
  frame (vs 0.16-0.18 for `Play` alone), only while the replay camera is
  in first person.

## What was built (2026-10-16, over c8c0edf6)

- `Data/AnimTrack`: `AnimLayerState` / `AnimLayerKey` / `AnimFloatKey` /
  `AnimYawKey`; `AddLayers` (every frame) keys a layer on a state or
  crossfade change or when `Advance(key, dt)` drifts > 0.02 in time,
  crossfade progress or weight (weight / progress rates measured over the
  last frame; a new crossfade's rate = progress / frame time);
  `AddFloats` (30 Hz) keys a float / the yaw when its extrapolation
  (`MaxExtrapolate` 1 s) drifts > 0.003 / 0.5 deg, and the held ids on a
  change. Values kept at file precision (times rounded down to the ms so
  a change shows on its own frame), so a track read back plays exactly as
  recorded (test).
- `Data/AttemptFormat`: `anim|`, `ak|<t>|<layer>|<hash>|<time>|<rate>|<weight>|<wrate>[|<next>|<ntime>|<nrate>|<p>|<prate>]`
  (`ak|<t>|<layer>|-` = off), `af|<t>|<i>=<v>:<rate>|...`,
  `ay|<t>|<yaw>|<rate>`, `ah|`. c8c0edf6's `a|` lines (never released)
  are skipped; its `af|` without a rate still parses.
- `Data/RunRecorder`: `AnimSource(snapshot, floats)` every frame of a
  running run, `floats` on the position tick.
- `Game/AnimReader`: per layer the current state, rate = `speed *
  timeScale / length`, weight, and in a crossfade next / progress; held
  ids from `InventoryReader.EquipmentIds(int[])` - the live
  `_equipmentSlots` views (c8c0edf6 read `_equipmentSlotsIds`, which only
  a save writes: the replay would have held the save's items all run).
- `Game/ArmsReplica.PoseLayers`: the crossfade replay (game-notes *What a
  replay must record*).
- `PracticeRunModule.Camera`: poses via `PoseLayers`; the replica is
  hidden when `EnsureArms` / `PoseAt` fails mid-replay (checker's fault).
- Docs: game-notes (rate = 1/length, crossfades, floats, live held
  slots), run-audit-and-replays.md section 2 (was "no animation is
  recorded").

Not done here: `InventoryReader.RefreshEquipped` (the Inventory tab's
"held" marks) still reads the stale `_equipmentSlotsIds` - a separate bug
for a task.
